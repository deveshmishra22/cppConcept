Capstone-Work1: Smart Office Access System

You already made classes, inheritance, virtual dispatch and overloading work together once, in the RR Skillverse course tracker. This exercise asks you to do it again, from scratch, on a use case that looks nothing like a course tracker — a building badge system where an employee, a contractor and a visitor can all be standing at the same door, and each one needs a different answer.

Brings together: classes → inheritance → overloadingCase study: Smart Office Access SystemEstimated time: 40-50 minutesRepo file: 08-ClassesandObjects/smart_office_access_system.cpp

Picture this: you're building the badge system for a smart office building. Every morning it has to decide, instantly, whether to let someone through the turnstile — an employee with standing access, a contractor whose engagement might have quietly expired, or a visitor who is still waiting on someone at the front desk to approve them. The building can't afford three unrelated access checks bolted together with duplicate reporting logic; it needs one gate that asks every person the same question and trusts each role to answer it correctly on its own terms.

What this exercise pulls together

Classes & objectsOne Person type owns the badge data every role shares, instead of Employee, Contractor and Visitor each duplicating name/ID handling on their own.
Inheritance & abstract classesAn abstract Person base class with a virtual destructor lets every role be checked and cleaned up through one shared interface.
Virtual functions & runtime polymorphismprocessAccess() takes a single const Person&; virtual dispatch decides at runtime which role's canAccess() actually runs.
Function & operator overloadingOverloaded calculateCharge() functions and an overloaded operator== give the badge system a natural, calculator-like API.
WHY

Why one base class for three different access rules

An employee always gets in. A contractor only gets in while their contract is active. A visitor only gets in once someone has approved them. Handling each of those as an unrelated function invites duplicate reporting code that quietly drifts apart the moment one rule changes. So every role is a Person first: one abstract base class defines what anyone badging in must be able to do — say whether they're allowed in, describe their own status — and leaves the actual rule to whichever role is being asked.

The base class also owns the one thing every role has to agree on: what counts as the same person. operator== compares only the badge ID, on purpose — deciding that once, in the base class, means an Employee, a Contractor and a Visitor can all be compared to each other without writing that comparison three times.

WHAT

The complete sample program

This program compiles and runs as-is. Read it top to bottom before touching anything — it is the pattern your homework will extend, not a blank page.

smart_office_access_system.cpp
// Capstone exercise sample -- combines inheritance, abstract classes, virtual
// dispatch, function overloading and operator overloading in one program.
//
// Use case: a smart office building that has to grant or deny badge access to
// employees, contractors and visitors -- each under a different rule -- without
// giving each type its own reporting logic.
#include <iostream>
#include <string>
using namespace std;

// Every person who badges in is a Person first (inheritance).
class Person {
protected:
    string name;
    int id;

public:
    Person(const string& n, int i) : name(n), id(i) {}
    virtual ~Person() = default;

    // Pure virtual functions: every concrete role must define its own rule (abstract class).
    virtual bool canAccess() const = 0;
    virtual string statusLine() const = 0;

    virtual void display() const {
        cout << name << " | ID: " << id << " | " << statusLine();
    }

    // Operator overloading: two people share a badge record if their IDs match,
    // regardless of which derived type either one is.
    friend bool operator==(const Person& a, const Person& b) {
        return a.id == b.id;
    }
};

// One function, every role: virtual dispatch decides the rest at runtime.
void processAccess(const Person& person) {
    person.display();
    cout << " -> " << (person.canAccess() ? "GRANTED" : "DENIED") << "\n";
}

class Employee : public Person {
public:
    Employee(const string& n, int i) : Person(n, i) {}
    bool canAccess() const override { return true; }
    string statusLine() const override { return "Employee"; }
};

class Contractor : public Person {
    bool contractActive;
public:
    Contractor(const string& n, int i, bool active)
        : Person(n, i), contractActive(active) {}
    bool canAccess() const override { return contractActive; }
    string statusLine() const override {
        return contractActive ? "Contractor (active)" : "Contractor (expired)";
    }
};

class Visitor : public Person {
    bool approved;
public:
    Visitor(const string& n, int i, bool appr)
        : Person(n, i), approved(appr) {}
    bool canAccess() const override { return approved; }
    string statusLine() const override {
        return approved ? "Visitor (approved)" : "Visitor (not approved)";
    }
};

// Function overloading: two ways to price a desk booking.
double calculateCharge(int wholeHours) {
    return wholeHours * 50.0;
}
double calculateCharge(double hours, double ratePerHour) {
    return hours * ratePerHour;
}

int main() {
    Employee rahul("Rahul", 101);
    Contractor priya("Priya", 202, true);
    Contractor amit("Amit", 203, false);
    Visitor sarah("Sarah", 301, true);
    Visitor john("John", 302, false);

    cout << "SMART OFFICE ACCESS REPORT\n---\n";
    processAccess(rahul);
    processAccess(priya);
    processAccess(amit);
    processAccess(sarah);
    processAccess(john);

    cout << "\nDesk booking, 4 whole hours: Rs " << calculateCharge(4) << "\n";
    cout << "Desk booking, 2.5 hours @ Rs 60/hr: Rs " << calculateCharge(2.5, 60.0) << "\n";

    Visitor sarahAgain("Sarah Verma", 301, true);
    cout << "\nSame badge ID? sarah == sarahAgain -> " << (sarah == sarahAgain ? "true" : "false") << "\n";
    cout << "Same badge ID? priya == amit -> " << (priya == amit ? "true" : "false") << "\n";
}
Expected outputSMART OFFICE ACCESS REPORT --- Rahul | ID: 101 | Employee -> GRANTED Priya | ID: 202 | Contractor (active) -> GRANTED Amit | ID: 203 | Contractor (expired) -> DENIED Sarah | ID: 301 | Visitor (approved) -> GRANTED John | ID: 302 | Visitor (not approved) -> DENIED Desk booking, 4 whole hours: Rs 200 Desk booking, 2.5 hours @ Rs 60/hr: Rs 150 Same badge ID? sarah == sarahAgain -> true Same badge ID? priya == amit -> false

Run it in VS Code

  1. Create a folder named capstone-work1 and open it in VS Code.
  2. Save the code above as smart_office_access_system.cpp (it also lives in the repo at 08-ClassesandObjects/smart_office_access_system.cpp).
  3. Compile with g++ -std=c++17 smart_office_access_system.cpp -o office.
  4. Run office.exe on Windows or ./office on Linux/macOS.
  5. Compare your terminal output line-by-line against the expected output above before you change anything.
Before you extend it: find the line that decides Amit is denied even though he's a Contractor exactly like Priya, and explain out loud why sarah == sarahAgain is true even though their names differ. If that's clear, you understand exactly what canAccess() and operator== are each responsible for — and you are ready for the task below.
HOW

Your task

Homework / assessment

Add an Intern role, then a third way to price a booking

The building just started an internship program. An intern only gets through the door once two separate conditions are both true: their mentor has approved them, and they've completed building induction. Like every other role, it needs its own definition of "allowed in," but it should show up correctly everywhere a Person already works — processAccess() and operator== included.

  1. Add a class Intern that inherits from Person and stores whether a mentor has approved them and whether induction is complete.
  2. Implement canAccess() so it returns true only when both conditions hold, and implement statusLine() to describe the intern's current state.
  3. Create one Intern in main() and pass them to processAccess() without changing that function at all.
  4. Add a third overload of calculateCharge() that takes no arguments and returns a fixed, default day-pass rate — print a confirmation message from inside it.
  5. Re-run the program and confirm that an intern with mentor approval but incomplete induction is still reported as DENIED.

Hints, not the answer

  • Your Intern constructor only needs to pass the name and ID up to Person's constructor — mentor approval and induction status are extra members that your own overrides read, the same way Contractor already reads contractActive.
  • You should not need to touch processAccess() or operator== at all. If a correctly written Intern doesn't automatically work with both, something about your override is wrong — check that every pure virtual function is implemented with a matching signature.
  • A zero-argument calculateCharge() is already unambiguous next to the other two overloads purely by how many arguments are passed — the compiler never has to guess which one you meant.
  • Before writing canAccess(), decide honestly: should mentor approval alone ever be enough? Keep the comparison as direct as Contractor's already is.

Polymorphism · Module 3

Compile-time polymorphism

Let the compiler choose the right operation from the types and arguments we provide.

⏱ Half day▣ Guided practice⌘ C++17

Function overloading lets you give related operations the same name and let the compiler pick the right version based on argument types — all at compile time.

WHY

Why one name matters more than you think

When you write a function called display(int), then later need display(double), the choices are: rename it displayDouble(), or overload it. Renaming means every call site must decide which name to use — now the caller's code contains knowledge that rightly belongs inside the library.

As the number of supported types grows, the naming problem compounds. Overloading keeps the calling code clean: the right function is chosen by the compiler from the types the caller already has.

WHAT

How the compiler selects an overload

  • overload resolution — the process the compiler runs when it sees a function call. It considers all functions with that name that are visible, ranks them by how well the argument types match, and picks the best. This happens entirely at compile time.
  • overloading on return type alone is not allowed — two functions that differ only in what they return are ambiguous; the compiler cannot pick from a call site where the return value is discarded.
  • default arguments are different from overloading — they provide fallback values, not type-based selection.
HOW

Three overloads of add() — one for each type

The same function name works for integers, doubles, and strings. The compiler picks the correct version at compile time based solely on the argument types supplied at the call site.

overload_demo.cpp
#include <iostream>

int add(int a, int b)       { return a + b; }
double add(double a, double b) { return a + b; }
std::string add(const std::string& a, const std::string& b) { return a + b; }

int main() {
    std::cout << add(2, 3)            << "\n";   // int overload: 5
    std::cout << add(1.5, 2.5)        << "\n";   // double overload: 4
    std::cout << add("hi, ", "world") << "\n";   // string overload: hi, world
}
Expected output5 4 hi, world
Try:
  1. Compile: g++ -std=c++17 overload_demo.cpp -o overload_demo
  2. Run on Windows: overload_demo.exe — Linux/macOS: ./overload_demo
  3. Experiment: Try calling add(2, 2.5) — one int, one double. The compiler cannot pick the best match and will report an ambiguity error. This is the compiler telling you the call is unclear.

Operator overloading gives a class meaningful behavior for built-in operators. It does not invent new operators or change how they work on built-in types.

WHY

Why write a + b instead of a.add(b)

When a type truly represents a mathematical or data-oriented value, operators make code read like the domain it models. A force vector addition written as forceA + forceB is immediately understandable to anyone who has read the physics specification; forceA.combinedWith(forceB) is longer and adds nothing.

The risk is misuse: an operator must be intuitive. If operator+ on a file object does something unexpected, every reader of the code will be confused. The rule: overload only when the operator's meaning for your type is obvious without a comment.

WHAT

Which operators can be overloaded and how

  • operator+, operator-, operator*, operator/ — arithmetic, typically return a new value
  • operator==, operator!=, operator< — comparison, return bool
  • operator<< — typically overloaded as a free function for stream output: std::ostream& operator<<(std::ostream& os, const Type& t)
  • operator= — assignment, already provided by the compiler if not defined; overload when your class manages a resource
  • operators you cannot overload: ::, .*, ., ?: — these are built into C++ syntax itself
HOW

A 2D vector type with arithmetic and comparison operators

This Vector2D struct adds operator+ as a member function and operator<< as a free function, which is the standard pattern for stream output.

vector2d.cpp
#include <iostream>

struct Vector2D {
    double x, y;

    Vector2D operator+(const Vector2D& other) const {
        return {x + other.x, y + other.y};
    }

    bool operator==(const Vector2D& other) const {
        return x == other.x && y == other.y;
    }
};

std::ostream& operator<<(std::ostream& os, const Vector2D& v) {
    return os << "(" << v.x << ", " << v.y << ")";
}

int main() {
    Vector2D a{3.0, 4.0};
    Vector2D b{1.0, 2.0};
    std::cout << a + b << "\n";
    std::cout << (a == b ? "equal" : "different") << "\n";
}
Expected output(4, 6) different
Try:
  1. Compile: g++ -std=c++17 vector2d.cpp -o vector2d
  2. Run on Windows: vector2d.exe — Linux/macOS: ./vector2d
  3. Experiment: Add operator- for subtraction. Then try overloading operator* to scale a vector by a scalar double — you'll need it as a free function: Vector2D operator*(const Vector2D& v, double s).

The Complex number type shows operator overloading at its most natural: two components that add independently.

WHY

Why Complex is the textbook operator-overloading example

A complex number z = a + bi has a real part (a) and an imaginary part (b). Addition follows one rule: add each part separately. This maps so directly to operator+ that the implementation writes itself.

More importantly, it demonstrates the value of wrapping two coupled pieces of data into one type with its own arithmetic — the same pattern used by 2D point, RGB colour, quaternion, and currency types in real codebases.

WHAT

The member function vs free function choice

  • member operator+(const T& other) const — access private members naturally; the left operand is *this
  • free function operator+(const T& a, const T& b) — allows the left operand to be any implicitly convertible type; needed for mixed arithmetic like 2.0 + complex
  • For symmetric operators (+, *), prefer free functions for symmetry; for assignment operators (+=, =), prefer member functions
HOW

Complete Complex class with addition, multiplication, and stream output

Private real and imaginary members, arithmetic operators implemented as member functions, and operator<< as a free function so the class can be printed naturally with std::cout.

complex_number.cpp
#include <iostream>

class Complex {
    double real_;
    double imag_;
public:
    Complex(double r, double i) : real_(r), imag_(i) {}

    Complex operator+(const Complex& other) const {
        return {real_ + other.real_, imag_ + other.imag_};
    }

    Complex operator*(const Complex& other) const {
        return {real_ * other.real_ - imag_ * other.imag_,
                real_ * other.imag_ + imag_ * other.real_};
    }

    bool operator==(const Complex& other) const {
        return real_ == other.real_ && imag_ == other.imag_;
    }

    double real() const { return real_; }
    double imag() const { return imag_; }
};

std::ostream& operator<<(std::ostream& os, const Complex& c) {
    return os << c.real() << " + " << c.imag() << "i";
}

int main() {
    Complex a{2.0, 3.0};
    Complex b{1.5, 4.0};

    std::cout << "Sum:     " << a + b << "\n";
    std::cout << "Product: " << a * b << "\n";
    std::cout << "Equal:   " << (a == b ? "yes" : "no") << "\n";
}
Expected outputSum: 3.5 + 7i Product: -9 + 12.5i Equal: no
Try:
  1. Compile: g++ -std=c++17 complex_number.cpp -o complex_number
  2. Run on Windows: complex_number.exe — Linux/macOS: ./complex_number
  3. Experiment: Add operator- for subtraction and operator*(double scalar) to scale a complex number. Then try Complex{0, 1} * Complex{0, 1} — this should give -1 + 0i (imaginary unit squared equals -1).

Point comparison shows the most common use of operator overloading: making equality behave correctly for domain types.

WHY

Why struct comparison doesn't work by default

C++ structs do not automatically support ==. Writing if (p1 == p2) without overloading fails to compile — the compiler has no idea whether "equal" means same pointer, same x, same x-and-y, or same coordinate within a tolerance.

This is deliberate: equality for domain types requires a domain decision. Is a GPS coordinate equal if it's within 1 metre? Within 1 millimetre? Exactly? The answer depends on the application.

WHAT

Design questions before writing operator==

  • What does equality mean for this type? Write it in one sentence before you write any code.
  • For floating-point types, exact equality is often wrong — prefer a tolerance comparison: std::abs(x - other.x) < 1e-9
  • Provide operator!= too (in C++17 you can derive it from operator==; in C++20 use = default to generate it automatically)
  • If you overload operator<, consider providing a full set: <, <=, >, >=, or use C++20 spaceship <=> to generate them all
HOW

Point with epsilon equality and lexicographic ordering

Floating-point operator== uses an epsilon tolerance so that coordinates differing by less than 1e-9 still compare equal. operator< enables sorting: sort by x first, then by y.

point_comparison.cpp
#include <iostream>
#include <cmath>

struct Point {
    double x, y;

    bool operator==(const Point& other) const {
        const double eps = 1e-9;
        return std::abs(x - other.x) < eps &&
               std::abs(y - other.y) < eps;
    }

    bool operator!=(const Point& other) const { return !(*this == other); }

    bool operator<(const Point& other) const {
        if (x != other.x) return x < other.x;
        return y < other.y;
    }
};

std::ostream& operator<<(std::ostream& os, const Point& p) {
    return os << "(" << p.x << ", " << p.y << ")";
}

int main() {
    Point checkpoint{10.0, 20.0};
    Point player{10.0, 20.0};
    Point enemy{5.0, 15.0};

    std::cout << "Player at checkpoint: " << (player == checkpoint ? "YES" : "NO") << "\n";
    std::cout << "Enemy at checkpoint:  " << (enemy  == checkpoint ? "YES" : "NO") << "\n";
    std::cout << "Sorted order: " << enemy << " comes before " << checkpoint
              << ": " << (enemy < checkpoint ? "true" : "false") << "\n";
}
Expected outputPlayer at checkpoint: YES Enemy at checkpoint: NO Sorted order: (5, 15) comes before (10, 20): true
Try:
  1. Compile: g++ -std=c++17 point_comparison.cpp -o point_comparison
  2. Run on Windows: point_comparison.exe — Linux/macOS: ./point_comparison
  3. Experiment: Change the player position to {10.0, 20.000000001} and rerun — with exact equality it would fail, but with the epsilon tolerance it still passes. This is why floating-point comparison is a design decision, not a technical default.
🎬 Story Mode

Three problems, one Friday afternoon

The Nimbus Games scoring and physics team had three features due by end of day. Combo scores that work with whole numbers and decimals. Knockback forces that combine the way arrows do on a whiteboard. Checkpoint detection that reads like plain English. None of it needs a new runtime feature — all of it is resolved by the compiler before the game even starts running.

The scoring system awards whole-number combo points during normal play, but decimal bonus multipliers during double-score events. Writing two different function names — addComboScore() and addBonusMultiplier() — would work, but every call site would have to remember which name applied when. Function overloading lets you write total(int, int) and total(double, double) under the same name. The compiler reads the argument types at each call site and picks the right version automatically, at compile time, before the game ships. One name. Two implementations. Zero confusion at the call site.

The physics programmer had drawn knockback on the whiteboard as forceA + forceB for six months. Making the code say combined = forceA.applyTo(forceB) instead would fight that mental model on every single line. Operator overloading lets you give the + operator a meaning for your own types. Vector2D operator+(const Vector2D& b) makes the C++ read exactly like the physics diagram. One rule: an overloaded operator must do what it looks like it does — combine vector components, nothing else. No hidden side effects, no surprises for the reader.

To teach how overloading works on paired values, the course uses complex numbers — and for good reason. A Complex value has a real part and an imaginary part. When you add two complex numbers, the real parts add independently and the imaginary parts add independently: (3 + 2i) + (1 + 4i) = (4 + 6i). That is exactly how a 2D physics force adds: horizontal plus horizontal, vertical plus vertical. The math is identical. Wrapping it behind operator+ means the calling code never manually juggles two components at once.

Every frame, the game checks one question for every checkpoint: is the player there? Without operator==, that check is p.x == cp.x && p.y == cp.y — copy-pasted at every checkpoint in the codebase, and wrong the day someone adds a z coordinate and forgets to update one copy. With operator overloading, the check reads: player == checkpoint. One line. It lives in one place. When the type changes, you fix the operator once and every call site is automatically correct.

Overload resolution is decided before the game runs a single frame. The compiler already knows which version of total() it is calling, at every call site, before the first player connects.

What we just learned

  • Function overloading — same function name, different parameter types; the compiler picks the right version at compile time based on argument types
  • Operator overloading — give a built-in operator a meaning for your own type; it must always do what the symbol looks like it does
  • Complex number addition — real parts add independently, imaginary parts add independently; the same pattern as any 2D paired value
  • operator== — centralizes equality logic in one place; prevents copy-paste bugs when the type grows or changes later

Also seen in the wild

FinanceAn interest calculator overloaded for int cents and double currency amounts uses the same function-overloading idea as the scoring system.
GIS & mapsMapping software overloads == and + on coordinate types the same way the game checks checkpoint position.
CAD softwareCombining 2D/3D transforms with + or * is the same operator-overloading judgment call as the force-vector problem.

Complete use case

Geometry inspection report

This program combines an overloaded function with operator overloads. It checks whether two recorded points match and calculates two measurements.

#include <iostream>

struct Point {
    int x;
    int y;
    bool operator==(const Point& other) const {
        return x == other.x && y == other.y;
    }
};

int total(int first, int second) { return first + second; }
double total(double first, double second) { return first + second; }

int main() {
    Point expected{120, 80};
    Point measured{120, 80};

    std::cout << "Point check: "
              << (expected == measured ? "PASS" : "REVIEW") << '\n';
    std::cout << "Integer total: " << total(120, 80) << '\n';
    std::cout << "Decimal total: " << total(12.5, 7.25) << '\n';
}

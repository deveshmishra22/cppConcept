Polymorphism · Module 3

Compile-time polymorphism

Let the compiler choose the right operation from the types and arguments we provide.

⏱ Half day▣ Guided practice⌘ C++17
01 · The idea

One name, different parameter lists

Function overloading lets related operations share one readable name. The compiler selects a function using the number, order, and types of arguments. The return type alone is not enough to create an overload.

Think of it like a C# method overload. The call site supplies the clue, and overload resolution happens before the program runs.
int add(int left, int right);
double add(double left, double right);

add(2, 3);          // int version
add(2.5, 3.5);      // double version
02 · The idea

Make domain values feel natural

Operator overloading gives a user-defined type meaningful behavior for familiar operators such as +, ==, and <. It does not invent a new operator or change how an operator works for built-in types.

Good fitValue-like types such as money, points, vectors, and complex numbers.
GuardrailKeep the behavior predictable. A plus operator should not secretly delete a file.
Complex operator+(const Complex& other) const;
bool operator==(const Point& other) const;
03 · Worked concept

Complex numbers as a value type

A complex number has a real part and an imaginary part. Addition is performed component by component, which makes operator+ a clear and useful abstraction.

Complex first{2.0, 3.0};
Complex second{1.5, 4.0};
Complex total = first + second;

// total is 3.5 + 7.0i

The calling code expresses the problem, while the class owns the arithmetic rule.

04 · Worked concept

Comparing points safely

A point comparison can mean different things. Here, equality means both coordinates match exactly. In production geometry code, decide explicitly whether floating-point tolerance is required.

Point expected{10, 20};
Point actual{10, 20};

if (actual == expected) {
    std::cout << "Coordinates match\n";
}
Design question: Before overloading an operator, write one sentence describing what the operator means for your type.
🎬 Story Mode

The scoreboard problem

Picture this: same studio, new problem. Nimbus Games' physics and scoring team needs three things by Friday: combo scores that can be whole numbers or decimals under one function name, knockback forces that combine the way arrows in a diagram would, and a reliable way to tell whether a player has actually reached a checkpoint. None of it needs a new runtime feature — all of it is decided before the game even starts running.

ACT 1

One scoring function, two kinds of points

The scoring system awards whole-number combo points most of the time, but decimal bonus multipliers during double-score events. Writing addComboScore() and addBonusScore() as separate names would work, but it would also make every call site remember which one applies. Overloading total(int, int) and total(double, double) lets the designer-facing code just say total(a, b) and trust the compiler to pick correctly, every time, before the game ships.

ACT 2

Forces should combine like forces, not like function calls

The physics programmer's whiteboard already draws knockback as forceA + forceB. Making the code say combined = forceA.applyTo(forceB) instead would fight that mental model on every line. Overloading + lets the C++ read the way the physics is actually described — as long as the team agrees, in writing, what + is allowed to mean for a force. It should combine components. It should never, say, also reset a cooldown timer as a side effect.

ACT 3

Two numbers that move together

A Complex value's real and imaginary parts add component by component — and that is precisely how a 2D knockback force's horizontal and vertical components combine too. The math the course teaches through complex numbers is the same math the physics team ships: two paired values, added independently, wrapped behind one clean operator+ so the calling code never manually juggles two components at once.

ACT 4

Did the player actually reach the checkpoint?

Every frame, the game asks one question: does the player's current Point match the checkpoint's Point? Without operator==, that check becomes a hand-written x == other.x && y == other.y copy-pasted at every checkpoint in the game. With it, the check reads exactly like the design document: player == checkpoint.

Overload resolution happens before your game even starts running — the compiler already knows which version of total() it's going to call, for every call site, before the first frame renders.

Also seen in the wild

FinanceAn interest calculator overloaded for int cents and double currency amounts mirrors Act 1's total() exactly.
GIS & mapsMapping software overloads == and + on coordinate types the same way Act 4 checks a checkpoint.
CAD softwareCombining 2D/3D transforms with + or * is the same operator-overloading judgment call as Act 2's force vectors.
Bring it back: the geometry inspection report below is Act 1 and Act 4 running together in one small program. Module 4 moves from "the compiler picks the right thing" to "the program survives when something goes wrong."

Overload a calculator function

#include <iostream>

int add(int left, int right) { return left + right; }
double add(double left, double right) { return left + right; }

int main() {
    std::cout << add(2, 3) << '\n';
    std::cout << add(2.5, 3.5) << '\n';
}

02

Add two complex values

#include <iostream>

class Complex {
    double real_;
    double imaginary_;
public:
    Complex(double real, double imaginary) : real_(real), imaginary_(imaginary) {}
    Complex operator+(const Complex& other) const {
        return {real_ + other.real_, imaginary_ + other.imaginary_};
    }
    void print() const { std::cout << real_ << " + " << imaginary_ << "i\n"; }
};

int main() {
    (Complex{2, 3} + Complex{1.5, 4}).print();
}
g++ -std=c++17 step2_complex.cpp -o step2_complex && ./step2_complexOutput: 3.5 + 7i
03

Compare two points

#include <iostream>

struct Point {
    int x;
    int y;
    bool operator==(const Point& other) const {
        return x == other.x && y == other.y;
    }
};

int main() {
    Point saved{10, 20};
    Point received{10, 20};
    std::cout << (saved == received ? "match" : "different") << '\n';
}
g++ -std=c++17 step3_point.cpp -o step3_point && ./step3_pointOutput: match
Complete use case

Geometry inspection report

This program combines an overloaded function with operator overloads. It checks whether two recorded points match and calculates two measurements.

#include <iostream>

struct Point {
    int x;
    int y;
    bool operator==(const Point& other) const {
        return x == other.x && y == other.y;
    }
};

int total(int first, int second) { return first + second; }
double total(double first, double second) { return first + second; }

int main() {
    Point expected{120, 80};
    Point measured{120, 80};

    std::cout << "Point check: "
              << (expected == measured ? "PASS" : "REVIEW") << '\n';
    std::cout << "Integer total: " << total(120, 80) << '\n';
    std::cout << "Decimal total: " << total(12.5, 7.25) << '\n';
}
g++ -std=c++17 program.cpp -o program && ./programPoint check: PASS · Integer total: 200 · Decimal total: 19.75

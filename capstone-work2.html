Capstone-Work2: Nimbus Logistics Challenge

Every earlier capstone gave you a complete, working program and asked you to bolt on one new class. This one is different: it's a single program with five features, and only two are finished. The other three are yours — the file compiles and runs today, but three of its answers are honest placeholders that tell you exactly what's missing. Your job is to replace each placeholder with real logic, one feature at a time, re-running after every change.

Brings together: Modules 1 → 2 → 3 → 4 → 5 → 6Case study: Nimbus Logistics order fulfillment engineEstimated time: 60-75 minutesRepo file: 24-Exercises/3_nimbus_logistics_challenge.cpp

Picture Nimbus Logistics: a warehouse holding real stock, and three kinds of orders arriving against it. The engine has to look an item up generically, price shipping differently depending on which kind of order it is, apply a discount using the right one of two overloaded rules, and refuse an order outright if the quantity requested doesn't make sense — all without any one part of the program needing to know how another part is built. That's not one concept, it's six, wired together the way a real small system actually is.

What this challenge pulls together

Module 1 — C++ BasicsA plain InventoryItem struct and functions taking const reference parameters carry the warehouse's raw data.
Module 2 — Inheritance & PolymorphismAn abstract Order base class; placeOrder() takes a const Order& and virtual dispatch decides which concrete order actually runs.
Module 3 — Compile-time PolymorphismTwo overloaded applyDiscount() functions, and an overloaded operator<< that prints any Order correctly.
Module 4 — Exception HandlingTwo custom exception types and a multi-catch block that tells an invalid order apart from an out-of-stock one.
Module 5 — Templates & GenericsA class template Repository<T> that stores any record type with an id field, not just this one.
Module 6 — STL & Containersstd::vector, std::find_if, and a closing range-based for loop over the final warehouse state.
WHY

Why this challenge doesn't just hand you a finished program

Reading a complete program and adding one independent class next to it — the pattern in the earlier capstones — proves you can copy a shape. It doesn't prove you can finish someone else's thought. Every real codebase you'll touch after this course looks exactly like this file: mostly working, with a few pieces genuinely missing, and your job is to read what's already there closely enough to slot the right logic into the right place without breaking anything around it.

So this file gives you the two features that establish the pattern — a working generic Repository<T> and a working StandardOrder — fully implemented, on purpose, so you have something correct to model the rest on. The other three raise std::logic_error("Feature N not implemented...") exactly where real logic belongs. The program still compiles and runs today; it just tells you the truth about what it can't do yet, one feature at a time, instead of failing to build at all.

WHAT

The starter file — run it before you change anything

This compiles and runs as-is. Read every GIVEN section top to bottom first — Repository<T> and StandardOrder are the two features already done, and they are the exact pattern the three TODOs follow.

3_nimbus_logistics_challenge.cpp
// CHALLENGE MODE — Nimbus Logistics: Generic Order Fulfillment Engine
//
// Brings together Modules 1-6:
//   Module 1: structs, functions, const-reference parameters
//   Module 2: abstract base class, virtual dispatch
//   Module 3: function overloading, operator overloading
//   Module 4: custom exceptions, try/catch
//   Module 5: class templates
//   Module 6: STL containers + algorithms (vector, find_if, range-based for)
//
// This file has 5 features. TWO are already implemented for you (Feature 1
// and Feature 2) -- read them carefully, they are the pattern the other
// three follow. THREE are your job (Feature 3, 4, 5), marked with TODO.
//
// The file compiles and runs as-is. Every unfinished feature currently
// throws a clear "[TODO] ..." message instead of doing real work, so you can
// build and run after every single change and watch one message at a time
// turn into real output.
#include <iostream>
#include <vector>
#include <algorithm>
#include <string>
#include <stdexcept>
using namespace std;

// ---------- GIVEN: Module 1 — a plain data record ----------
struct InventoryItem {
    int id;
    string name;
    int stockQty;
    double unitPrice;
};

// ---------- Feature 1 (GIVEN): a generic Repository<T> ----------
// One container class, reusable for InventoryItem today and for any other
// type tomorrow, as long as that type has an `id` member. This is exactly
// the "write once, let the compiler specialise it" idea from Module 5,
// combined with the STL's find_if algorithm from Module 6.
template<typename T>
class Repository {
    vector<T> items;
public:
    void add(const T& item) { items.push_back(item); }

    T* findById(int id) {
        auto it = find_if(items.begin(), items.end(),
                           [id](const T& x) { return x.id == id; });
        return (it != items.end()) ? &(*it) : nullptr;
    }

    const vector<T>& all() const { return items; }
};

// ---------- GIVEN: Module 4 — custom exception types ----------
class InvalidQuantityException : public runtime_error {
public: explicit InvalidQuantityException(const string& msg) : runtime_error(msg) {}
};
class OutOfStockException : public runtime_error {
public: explicit OutOfStockException(const string& msg) : runtime_error(msg) {}
};

// ---------- GIVEN: Module 2 abstract base + Module 3 operator<< ----------
class Order {
protected:
    int itemId;
    int quantity;
public:
    Order(int id, int qty) : itemId(id), quantity(qty) {}
    virtual ~Order() = default;

    int getItemId() const { return itemId; }
    int getQuantity() const { return quantity; }

    virtual double shippingCost() const = 0;
    virtual string describe() const = 0;

    friend ostream& operator<<(ostream& os, const Order& o) {
        os << o.describe();
        return os;
    }
};

// ---------- Feature 2 (GIVEN): the simplest concrete Order ----------
class StandardOrder : public Order {
public:
    StandardOrder(int id, int qty) : Order(id, qty) {}
    double shippingCost() const override { return 50.0; }
    string describe() const override { return "Standard Order"; }
};

// ---------- Feature 3 (YOUR TASK): ExpressOrder ----------
//   - shippingCost(): 150.0 normally, 250.0 if sameDayRequested is true.
//   - describe(): "Express Order (same-day)" or "Express Order (standard speed)".
// Nothing else needs to change -- operator<< and placeOrder already work
// with ANY Order, including this one, through virtual dispatch.
class ExpressOrder : public Order {
    bool sameDayRequested;
public:
    ExpressOrder(int id, int qty, bool sameDay) : Order(id, qty), sameDayRequested(sameDay) {}

    double shippingCost() const override {
        throw logic_error("Feature 3 not implemented: ExpressOrder::shippingCost()");
    }
    string describe() const override {
        throw logic_error("Feature 3 not implemented: ExpressOrder::describe()");
    }
};

// ---------- Feature 4 (YOUR TASK): overloaded applyDiscount ----------
//   applyDiscount(double amount, double percentOff) -> reduce by a percentage.
//   applyDiscount(double amount, int flatOff)        -> reduce by a flat
//     rupee amount, but never return below 0.
double applyDiscount(double amount, double percentOff) {
    throw logic_error("Feature 4 not implemented: applyDiscount(double, double)");
}
double applyDiscount(double amount, int flatOff) {
    throw logic_error("Feature 4 not implemented: applyDiscount(double, int)");
}

// ---------- Feature 5 (YOUR TASK): stock validation ----------
//   - if requestedQty <= 0, throw InvalidQuantityException (check this FIRST).
//   - else if requestedQty > availableStock, throw OutOfStockException.
//   - otherwise return normally.
void validateOrderQuantity(int requestedQty, int availableStock) {
    throw logic_error("Feature 5 not implemented: validateOrderQuantity()");
}

// ---------- GIVEN: wiring it all together ----------
void placeOrder(Repository<InventoryItem>& repo, Order& order) {
    InventoryItem* item = repo.findById(order.getItemId());
    if (!item) { cout << "  Item not found.\n"; return; }
    item->stockQty -= order.getQuantity();
    double subtotal = item->unitPrice * order.getQuantity();
    double total = subtotal + order.shippingCost();
    cout << "  " << order << " | Item: " << item->name << " | Total: Rs " << total << "\n";
}

int main() {
    Repository<InventoryItem> warehouse;
    warehouse.add({1, "Wireless Mouse", 10, 799.0});
    warehouse.add({2, "Mechanical Keyboard", 3, 4499.0});
    warehouse.add({3, "USB-C Hub", 0, 1299.0}); // deliberately out of stock

    cout << "NIMBUS LOGISTICS - ORDER FULFILLMENT\n---\n";

    cout << "\n[Feature 2 - given] Standard order:\n";
    StandardOrder mouseOrder(1, 2);
    try { placeOrder(warehouse, mouseOrder); }
    catch (const logic_error& e) { cout << "  [TODO] " << e.what() << "\n"; }

    cout << "\n[Feature 3 - your task] Express orders:\n";
    ExpressOrder keyboardOrder(2, 1, true);
    ExpressOrder keyboardOrderNoRush(2, 1, false);
    try { placeOrder(warehouse, keyboardOrder); }
    catch (const logic_error& e) { cout << "  [TODO] " << e.what() << "\n"; }
    try { placeOrder(warehouse, keyboardOrderNoRush); }
    catch (const logic_error& e) { cout << "  [TODO] " << e.what() << "\n"; }

    cout << "\n[Feature 4 - your task] Discount overloads:\n";
    try {
        double percentResult = applyDiscount(1000.0, 10.0);
        cout << "  Rs 1000 with 10% off    -> Rs " << percentResult << "\n";
    } catch (const logic_error& e) { cout << "  [TODO] " << e.what() << "\n"; }
    try {
        double flatResult = applyDiscount(1000.0, 200);
        cout << "  Rs 1000 with Rs 200 off -> Rs " << flatResult << "\n";
    } catch (const logic_error& e) { cout << "  [TODO] " << e.what() << "\n"; }

    cout << "\n[Feature 5 - your task] Stock validation exceptions:\n";
    try {
        StandardOrder hubOrder(3, 1); // item 3 has 0 stock
        validateOrderQuantity(hubOrder.getQuantity(), 0);
        placeOrder(warehouse, hubOrder);
        cout << "  Unexpected: order should have failed (no exception thrown)\n";
    } catch (const OutOfStockException& e) { cout << "  Caught OutOfStockException: " << e.what() << "\n"; }
      catch (const logic_error& e) { cout << "  [TODO] " << e.what() << "\n"; }

    try {
        StandardOrder badOrder(1, 0); // invalid quantity
        validateOrderQuantity(badOrder.getQuantity(), 10);
        placeOrder(warehouse, badOrder);
        cout << "  Unexpected: order should have failed (no exception thrown)\n";
    } catch (const InvalidQuantityException& e) { cout << "  Caught InvalidQuantityException: " << e.what() << "\n"; }
      catch (const logic_error& e) { cout << "  [TODO] " << e.what() << "\n"; }

    cout << "\nFinal warehouse state:\n";
    for (const auto& item : warehouse.all()) {
        cout << "  #" << item.id << " " << item.name << " -> stock left: " << item.stockQty << "\n";
    }

    return 0;
}

Run it in VS Code

  1. Create a folder named capstone-work2 and open it in VS Code.
  2. Save the code above as 3_nimbus_logistics_challenge.cpp (it also lives in the repo at 24-Exercises/3_nimbus_logistics_challenge.cpp).
  3. Compile with g++ -std=c++17 3_nimbus_logistics_challenge.cpp -o nimbus_challenge.
  4. Run nimbus_challenge.exe on Windows or ./nimbus_challenge on Linux/macOS.
  5. Confirm your output matches "Output today" exactly before you change a single line — that proves your toolchain and the starter file are both fine.
Before you touch Feature 3: explain out loud why placeOrder() never had to change even once while you add ExpressOrder. If you can point at the line that makes that true, you understand exactly what virtual dispatch is buying you here — and you're ready for the three tasks below.
HOW

Your task — three features, in any order

Homework / assessment

Finish Feature 3, Feature 4, and Feature 5

Each feature below is independent — finishing one does not require finishing another, and each one's section of the output changes on its own the moment it's correct. Work through them in whatever order you like, recompiling and rerunning after each change.

  1. Feature 3 — ExpressOrder. Replace both throw logic_error(...) bodies in ExpressOrder. shippingCost() must return 150.0, or 250.0 when sameDayRequested is true. describe() must return "Express Order (same-day)" or "Express Order (standard speed)" to match. Do not touch placeOrder(), operator<<, or Order — they already work with any correctly written subclass.
  2. Feature 4 — applyDiscount overloads. Implement both functions. The double overload reduces amount by a percentage. The int overload subtracts a flat rupee value and must never return a negative result — clamp it to 0 if the subtraction would go below it.
  3. Feature 5 — validateOrderQuantity. Throw InvalidQuantityException when requestedQty is zero or negative, checked before anything else. Throw OutOfStockException when requestedQty exceeds availableStock. Return normally otherwise. Get the order of the two checks right, or a zero-quantity order against a fully-stocked item will report the wrong exception.
  4. Recompile and rerun after each feature. Compare your terminal output section-by-section against "Target output" above — each fixed feature should make exactly one section change, and no other section should move.

Hints, not the answer

  • Every TODO function already has the correct signature and is already called from the right place in main() and placeOrder() — you are filling in a body, not designing new wiring.
  • For Feature 3, look at exactly how StandardOrder answers the same two virtual functions a few lines above it. Same shape, different numbers and a condition on sameDayRequested.
  • For Feature 4, the compiler already knows which overload to call based on whether you pass a whole number or a decimal at the call site in main() — you don't need to do anything to make that selection happen, only to make each body correct once selected.
  • For Feature 5, re-read the two calls to validateOrderQuantity() near the bottom of main() — they tell you exactly which two situations must trigger which exception, including the values used to prove it.
  • If a section still prints [TODO] ... after you believe you're done, you edited the wrong function or left an old throw logic_error line in place — search the file for the literal text not implemented to make sure none are left in the feature you just touched.

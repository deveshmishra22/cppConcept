Capstone-Work3: Nimbus Fleet Command

Module 8 covered six different systems-level topics across six tabs. This challenge is one program that needs all six. It's a diagnostics agent with five features that currently throw a clear "not implemented" message, plus one structural requirement about how the finished program must be built — not just what it must do. The file compiles and runs today; your job is to replace each placeholder with real logic and then restructure the build itself.

Brings together: every Module 8 topic tabCase study: Nimbus Fleet Command diagnostics relay agentEstimated time: 70-90 minutesRepo files: 24-Exercises/4_nimbus_fleet_command_challenge.cpp, 24-Exercises/4_relay_server.cpp

Picture Nimbus Fleet Command: a diagnostics agent runs on every server rack, watches for trouble, and has to get one report out three different ways before it can trust the report is safe — over the network to a central relay, archived locally through a helper process in case the network is down, with a live system snapshot attached so nobody has to guess whether "slow" means "out of memory." None of that works if the agent copies gigabytes of readings it doesn't need to, and none of the alerts mean anything if the agent can't tell one kind of reading from another at run time.

What this challenge pulls together

Additional Topics — RTTIFeature 1: define NetworkEvent and complete the isCritical() dynamic_cast chain across all three event types.
Move SemanticsFeature 2: buildReport() takes ownership of a vector<unique_ptr<DiagnosticEvent>> by value — moved in, never copied.
Reading System InfoFeature 3: getSystemSnapshot() queries SYSTEM_INFO and MEMORYSTATUSEX and formats one line.
NetworkingFeature 4: sendReportOverTcp() connects and sends over a real TCP socket, failing softly if the relay isn't up.
Pipes & FDsFeature 5: archiveReportViaPipe() spawns a child process and hands it the report through an anonymous pipe.
LinkingConstraint: split the event hierarchy into its own static library, built with ar, and link against it instead of compiling it inline.
WHY

Why this one has a constraint, not just five TODOs

Every earlier capstone asked "can you write the missing logic?" This one adds a second question real systems work always asks: "did you build it the right way?" A function that computes the correct answer but is linked wrong — or a program that crashes the moment the relay server isn't running — is not actually finished, even if every unit of logic inside it is correct. Module 8 spent an entire tab on static vs dynamic linking for exactly this reason: how you build a program is a decision with consequences, not an afterthought once the code compiles.

So this file gives you five functions that throw std::logic_error("Feature N not implemented...") exactly where real logic belongs — the same honest-placeholder pattern as Capstone-Work2 — plus one requirement that isn't a function body at all: once your five features pass, you restructure the file itself so the event hierarchy lives in its own statically-linked library. The program compiles and runs today, throwing clear TODO messages; get all five features and the restructure right, and it becomes a small but genuine multi-file, multi-process system.

WHAT

The starter file — run it, and start the relay, before you change anything

This compiles and runs as-is. Read every GIVEN section first — the DiagnosticEvent/TempEvent/DiskEvent hierarchy, the NetworkEvent skeleton's fields and constructor, and child_main() are all done for you and establish the exact shape each TODO follows.

// ---------- GIVEN: DiagnosticEvent hierarchy ----------
struct DiagnosticEvent {
    string source;
    DiagnosticEvent(string s) : source(move(s)) {}
    virtual ~DiagnosticEvent() {}
    virtual string describe() const { return source + ": generic event"; }
};
struct TempEvent : DiagnosticEvent {
    double celsius;
    TempEvent(string s, double c) : DiagnosticEvent(move(s)), celsius(c) {}
    string describe() const override { return source + ": temperature " + to_string(celsius) + "C"; }
};
struct DiskEvent : DiagnosticEvent {
    int percentFull;
    DiskEvent(string s, int pct) : DiagnosticEvent(move(s)), percentFull(pct) {}
    string describe() const override { return source + ": disk " + to_string(percentFull) + "% full"; }
};

int child_main() {
    string line;
    if (getline(cin, line)) {
        ofstream log("archive_log.txt", ios::app);

// ---------- GIVEN: wiring it all together ----------
int main(int argc, char* argv[]) {
    if (argc >= 2 && string(argv[1]) == "archive")
        return child_main();

    vector<unique_ptr<DiagnosticEvent>> readings;
    readings.push_back(make_unique<TempEvent>("Rack-A", 94.5));
    readings.push_back(make_unique<DiskEvent>("Rack-B", 42));
    readings.push_back(make_unique<NetworkEvent>("Rack-C", 610));

    string report;
    try {
        report = buildReport(move(readings));
    } catch (const logic_error& e) {
        cout << "[TODO] " << e.what() << "\n";
        report = "=== Fleet Diagnostics Report (placeholder) ===\n";
    }

    try {
        report += getSystemSnapshot() + "\n";
    } catch (const logic_error& e) {
        cout << "[TODO] " << e.what() << "\n";
    }

    cout << report;

    try {
        if (sendReportOverTcp(report, "127.0.0.1", 9090))
            cout << "Report sent to relay.\n";
        else
            cout << "Could not reach relay (start relay_server.exe first).\n";

        cout << "[TODO] " << e.what() << "\n";

        if (archiveReportViaPipe(report))
            cout << "Report archived via pipe.\n";
        else
            cout << "Archiver pipe failed.\n";
    } catch (const logic_error& e) {
        cout << "[TODO] " << e.what() << "\n";
    }
}

Run it in VS Code

  1. Create a folder named capstone-work3 and open it in VS Code.
  2. Save the code above as 4_nimbus_fleet_command_challenge.cpp, and copy relay_server.cpp into the same folder (both live in the repo at 24-Exercises/, filenames 4_nimbus_fleet_command_challenge.cpp and 4_relay_server.cpp).
  3. Compile the agent: g++ -std=c++17 4_nimbus_fleet_command_challenge.cpp -o agent -lws2_32. Compile the relay: g++ -std=c++17 4_relay_server.cpp -o relay_server -lws2_32.
  4. Start relay_server.exe first, in its own terminal — restart it before every test run, since it exits after receiving one report.
  5. Run agent.exe in a second terminal. Confirm your output matches "Output today" exactly before you change a single line.

HOW

Your task — five features and one build constraint

Constraints — read before you start

Things that will compile fine and still be wrong

  • Exactly one WSAStartup/WSACleanup pair. Both belong inside sendReportOverTcp() for this exercise — don't call WSAStartup anywhere else, and don't skip WSACleanup on the failure path.
  • A failed connect is not an error. sendReportOverTcp() must return false and let main() print "Could not reach relay" — it must never throw or crash when relay_server.exe isn't running. Test both with and without the relay running.
  • Don't change buildReport's parameter to a reference. The whole point of Feature 2 is that the parameter is taken by value so the caller's vector is moved in. Changing it to const vector<...>& would "fix" a compile error the wrong way — unique_ptr has no copy constructor, so if you find yourself fighting the compiler here, you've mis-called the function in main(), not mis-declared it.
  • GlobalMemoryStatusEx fails silently if you forget dwLength. Set memStatus.dwLength = sizeof(memStatus) before the call, not after.
  • The pipe carries exactly one line. child_main() reads with a single std::getline. If your report string still contains '\n' characters when you write it to the pipe, the archiver only sees the first line — replace newlines (a space or | both work) before writing.
  • The linking constraint is not optional and not a TODO stub. A version that still compiles the event hierarchy directly into one .cpp file has not met the Linking requirement, even if all 5 features are correct. Submissions must show a separate rttilib.h/rttilib.cpp, a static library built with ar, and a final link step against that library.
Homework / assessment

Finish Features 1 through 5, then apply the Linking constraint

Each feature is independent — finishing one does not require finishing another, though Feature 2 calls Feature 1's isCritical(), so an unfinished Feature 1 will surface as a "[TODO] Feature 1..." message even while you're testing Feature 2. Work through the five features in whatever order you like, recompiling and rerunning after each change, then finish with the Linking restructure described in the constraints above.

  1. Feature 1 — NetworkEvent + isCritical. Implement NetworkEvent::describe() and the full isCritical() body with three dynamic_cast checks and their thresholds.
  2. Feature 2 — buildReport. Build the report string from the moved-in readings vector using describe() and isCritical().
  3. Feature 3 — getSystemSnapshot. Query SYSTEM_INFO and MEMORYSTATUSEX and format the one-line snapshot.
  4. Feature 4 — sendReportOverTcp. Connect and send over a real TCP socket, handling a failed connect gracefully.
  5. Feature 5 — archiveReportViaPipe. Spawn the archiver child process over an anonymous pipe and write the report to it.
  6. Linking constraint. Extract the event hierarchy into rttilib.h/rttilib.cpp, build a static library with ar, and link your main program against it.

Hints, not the answer

  • Every TODO function already has the correct signature and is already called from the right place in main() — you are filling in a body, not designing new wiring.
  • For Feature 1, look at how TempEvent::describe() and DiskEvent::describe() are written a few lines above NetworkEvent — same shape, different field and wording.
  • For Feature 3, the format string in the Reading System Info tab's own demo (sysinfo_step.cpp) uses exactly the same two API calls in exactly the same order.
  • For Feature 4 and Feature 5, the Networking and Pipes & FDs tabs' own HOW-block code cards are close to line-for-line what these two functions need — the difference is mostly which variable holds the data being sent.
  • For the Linking constraint, the Linking tab's rrmathlib.h/rrmathlib.cpp pair plus its three build commands (combined, static .a via ar, dynamic .dll) is the exact pattern — you only need the static-library path here, not the dynamic one.
  • If a section still prints [TODO] ... after you believe you're done, search the file for the literal text not implemented to make sure none are left in the feature you just touched.

Polymorphism / Module 2

Inheritance & Polymorphism

Extend the banking-system thinking from Module 1 into families of related types. We will start with code reuse, then see why virtual functions are needed when one interface must work with many concrete objects.

Day: 2 of 6Topics: 4Case study: Shape hierarchyRepo folder: 08-ClassesandObjects/

Inheritance expresses an intentional relationship: a derived type is a more specific form of a base type.

WHY

Why share a common interface?

Suppose a graphics system needs circles, rectangles, and triangles. They all have a position and a way to describe themselves, but each shape stores different details. Inheritance lets shared behavior live in one base type while derived classes add their own behavior.

Public inheritance should communicate an honest “is-a” relationship. It is not just a shortcut for copying code.

WHAT

Base and derived syntax

The colon introduces the base class: class Circle : public Shape. Public inheritance keeps the base public interface public on the derived object. A derived constructor calls the base constructor before its own body runs.

inheritancecls.cpp
#include <iostream>

class Shape {
public:
    void describe() const { std::cout << "A drawable shape\n"; }
};

class Circle : public Shape {
public:
    void drawCircle() const { std::cout << "Drawing a circle\n"; }
};

int main() {
    Circle circle;
    circle.describe();
    circle.drawCircle();
}

Run the repository example

  1. Open 08-ClassesandObjects/inheritancecls.cpp.
  2. Compile with g++ -std=c++17 inheritancecls.cpp -o inheritance_demo.
  3. Run inheritance_demo.exe on Windows or ./inheritance_demo on Linux/macOS.
Expected outputA drawable shape Drawing a circle
HOW

Constructor chaining: base runs before derived

When a derived object is constructed, the base class constructor runs first, before the derived constructor body. This guarantees the base part is fully initialised before derived code runs. The colon-initialiser syntax : Base(args) selects which base constructor to call.

constructor_chain.cpp
#include <iostream>

class Vehicle {
    std::string brand;
public:
    explicit Vehicle(std::string b) : brand(b) {
        std::cout << "Vehicle created: " << brand << "\n";
    }
    std::string getBrand() const { return brand; }
};

class Car : public Vehicle {
    int doors;
public:
    Car(std::string b, int d) : Vehicle(b), doors(d) {
        std::cout << "Car created with " << doors << " doors\n";
    }
    void info() const {
        std::cout << getBrand() << " has " << doors << " doors\n";
    }
};

int main() {
    Car c("Toyota", 4);
    c.info();
}
Expected outputVehicle created: Toyota Car created with 4 doors Toyota has 4 doors

Run it and experiment

  1. Save as constructor_chain.cpp, compile: g++ -std=c++17 constructor_chain.cpp -o chain
  2. Run on Windows: chain.exe — on Linux/macOS: ./chain
  3. Experiment 1: Add a Truck class inheriting from Vehicle with a payload (in tonnes). Notice the base constructor always runs first.
  4. Experiment 2: Remove the : Vehicle(b) from Car's initialiser list and recompile — the compiler error tells you exactly which base constructor is missing.

Inheritance alone reuses members. Polymorphism lets one base interface select the correct derived behavior at runtime.

WHY

Why a non-virtual function is not enough

If a Shape* points to a Circle, the compiler otherwise chooses the function based on the pointer's declared type. That is static binding. A virtual function asks C++ to choose the override based on the object that is actually there. This is dynamic binding.

WHAT

virtual, override, and dynamic dispatch defined

  • virtual — added to a base class member function, it tells the compiler: "when this function is called through a pointer or reference, choose the implementation based on the actual runtime type of the object, not the declared type of the pointer." Without virtual, the call is resolved at compile time from the pointer's declared type — this is static binding.
  • override (C++11) — added to a derived class function that is intended to override a base class virtual. The compiler verifies that a matching virtual exists in the base — if not, it's a compile-time error instead of a silent bug. Always use override when you mean to override.
  • vtable — how most compilers implement virtual dispatch. Every class with at least one virtual function gets a hidden table of function pointers (one per virtual function). Every object stores a hidden pointer (vptr) to its class's vtable. A virtual call follows the vptr, looks up the function in the table, and calls it — this is the runtime overhead, typically one pointer indirection.

In C#, all instance methods are effectively virtual by default and are dispatched through the CLR's virtual dispatch mechanism. In C++, virtual dispatch is opt-in and has zero cost until you add the virtual keyword.

HOW

Call through a base reference

polymorphismcls.cpp
#include <iostream>

class Shape {
public:
    virtual void draw() const { std::cout << "Generic shape\n"; }
    virtual ~Shape() = default;
};

class Circle : public Shape {
public:
    void draw() const override { std::cout << "Circle\n"; }
};

int main() {
    Circle circle;
    Shape& shape = circle;
    shape.draw();
}

override asks the compiler to check that the derived function really overrides a virtual base function. Use it whenever you intend overriding.

Expected outputCircle

Run it and experiment

  1. Open 08-ClassesandObjects/polymorphismcls.cpp, compile: g++ -std=c++17 polymorphismcls.cpp -o poly
  2. Run — you see Circle. The shape.draw() call dispatched to Circle::draw() at runtime.
  3. Experiment 1: Add a Rectangle class with void draw() const override. Create a Shape& r = rectangle; and call r.draw() — no if statement needed.
  4. Experiment 2: Remove virtual from Shape::draw() and recompile. Now shape.draw() prints Generic shape — the call is bound to Shape::draw() at compile time, ignoring the actual object type. This is static binding.
  5. Experiment 3: Rename Circle::draw() to Circle::Draw() (capital D) and keep override — the compiler error tells you no matching virtual was found. override caught the typo for you.

An abstract base class defines a contract but cannot be created directly.

WHY

Why make a class abstract?

When you write virtual double area() const with a body in Shape, you're forced to invent a "generic area" that doesn't make sense — a shape with no specific geometry has no meaningful area. If you return 0.0 as a default, derived classes that forget to override silently inherit the wrong answer.

Making area() pure virtual (= 0) turns that runtime bug into a compile-time error: any concrete derived class that fails to implement area() cannot be instantiated at all. The abstract base becomes a contract that the compiler enforces.

An abstract class also cannot be directly instantiated — Shape s; fails to compile. This prevents accidentally creating a meaningless "generic shape" that would corrupt a real computation.

WHAT

Pure virtual functions

Writing virtual double area() const = 0; makes the function pure virtual. Any concrete derived class must implement it before objects can be created. The base class becomes an interface-like contract for the rest of the program.

purevirtual-interfaces.cpp
class Shape {
public:
    virtual double area() const = 0;
    virtual ~Shape() = default;
};

class Rectangle : public Shape {
    double width;
    double height;
public:
    Rectangle(double w, double h) : width(w), height(h) {}
    double area() const override { return width * height; }
};
Design check: if a caller only needs to ask a shape for its area, it should depend on the Shape interface rather than know every future shape class.
What the compiler says if you write Shape s;error: cannot declare variable 's' to be of abstract type 'Shape'
HOW

A full abstract interface with two concrete shapes

This example puts both name() and area() as pure virtuals, then calls them through a common function that knows only the base interface:

abstract_shape.cpp
#include <iostream>
#include <string>

class Shape {
public:
    virtual std::string name() const = 0;
    virtual double area() const = 0;
    virtual ~Shape() = default;

    void printReport() const {
        std::cout << name() << " area: " << area() << "\n";
    }
};

class Circle : public Shape {
    double r;
public:
    explicit Circle(double r) : r(r) {}
    std::string name() const override { return "Circle"; }
    double area() const override { return 3.14159 * r * r; }
};

class Rectangle : public Shape {
    double w, h;
public:
    Rectangle(double w, double h) : w(w), h(h) {}
    std::string name() const override { return "Rectangle"; }
    double area() const override { return w * h; }
};

int main() {
    Circle c(5.0);
    Rectangle r(3.0, 4.0);
    c.printReport();
    r.printReport();
}
Expected outputCircle area: 78.5397 Rectangle area: 12

Run it and experiment

  1. Save as abstract_shape.cpp, compile: g++ -std=c++17 abstract_shape.cpp -o abstract_shape, run.
  2. Experiment 1: Add class Triangle : public Shape { double base, height; ... }. If you forget to implement either pure virtual, the compiler tells you exactly which one is missing.
  3. Experiment 2: Try adding Shape s; in main() and recompile. Read the error — "cannot declare variable of abstract type" is the contract enforcement working.
  4. Experiment 3: Add void printReport() const to Shape as a non-virtual function using area() and name(). The base class can safely call its own pure virtual functions — the vtable routes to the derived implementation at runtime.
Reference: cppreference: Abstract class — rules for pure virtual functions including what the base class is allowed to do with them.

A polymorphic base class needs a virtual destructor when objects may be destroyed through a base pointer.

WHY

Why virtual destruction matters

Shape* shape = new Circle; stores a derived object behind a base pointer. With a virtual destructor, delete shape runs the derived cleanup first and then the base cleanup. Without it, deleting through the base pointer is unsafe.

A vtable is an implementation technique commonly used to support virtual dispatch. Treat it as a useful mental model, not as a promise about one compiler's exact memory layout.

WHAT

Virtual destructor and vtable pointer defined

  • Virtual destructor — a destructor declared with virtual in the base class: virtual ~Shape() = default;. When delete ptr is called where ptr is a base-class pointer, the compiler looks up the destructor through the vtable — so the correct derived destructor runs first, then the base destructor. Without virtual, only the base destructor would run, leaving derived resources unreleased.
  • Rule of thumb: if a class has any virtual function (making it a polymorphic base), give it a virtual destructor. If you want no destructor logic, write virtual ~Base() = default;.
  • vtable pointer (vptr): every object of a class that has virtual functions contains a hidden pointer — the vptr — pointing to that class's vtable. Calling a virtual function reads the vptr, looks up the function in the table, and jumps to it. This adds one pointer of memory per object and one indirection per virtual call — the only overhead virtual functions carry.
HOW

The memory leak and the fix

Removing virtual from the base destructor is a real production bug. This example makes the consequence visible:

virtual_destructor.cpp
#include <iostream>

class Resource {
public:
    Resource()  { std::cout << "Resource acquired\n"; }
    virtual ~Resource() { std::cout << "Resource released\n"; }
};

class ManagedBuffer : public Resource {
    int* buffer;
public:
    ManagedBuffer() : buffer(new int[1024]) {
        std::cout << "Buffer allocated (4 KB)\n";
    }
    ~ManagedBuffer() override {
        delete[] buffer;
        std::cout << "Buffer freed\n";
    }
};

int main() {
    Resource* r = new ManagedBuffer();
    delete r;
    // With virtual ~Resource: ~ManagedBuffer runs THEN ~Resource
    // Without virtual:        only ~Resource runs — buffer leaks every time
}
Expected output (with virtual destructor)Resource acquired Buffer allocated (4 KB) Buffer freed Resource released

Prove the leak yourself

  1. Save as virtual_destructor.cpp, compile: g++ -std=c++17 virtual_destructor.cpp -o vdtor, run — observe all four lines print.
  2. Experiment: Change virtual ~Resource() to just ~Resource() (remove virtual). Recompile and run — "Buffer freed" disappears. The buffer is leaked every time the program runs this scenario.
  3. On Linux, run with valgrind ./vdtor to confirm 4096 bytes are leaked. This is exactly the scenario Rule of Five addresses.
Reference: cppreference: Destructor — virtual destructors, order of destruction, and the Rule of Five.

🎬 Story Mode

One loop, every shape

Priya was building the render loop for Nimbus Games' new engine. The scene had circles. It had rectangles. Next sprint it would have triangles. Her lead engineer set one rule: the render loop may not contain a single if (type == "circle"). It must be able to draw every shape without knowing what it is holding. This module is how she made that work.

Circles and rectangles look different, but they share real things: a position, a color, a need to be drawn, a hitbox for collision. Priya started by defining what every on-screen object has in common and put that in a Shape base class. Then: class Circle : public Shape. That colon is not just code reuse — it is a real claim. A circle is a shape. It inherits everything Shape defined and adds its own radius on top. Inheritance is the mechanism; "is-a" is the relationship it represents. The render loop can then hold a list of Shape* and not care what concrete type each pointer points to.

The render loop holds a vector<Shape*> — hundreds of mixed objects per frame. It calls shape->draw() in one loop for all of them. Without the keyword virtual, C++ would always run Shape::draw() no matter what the pointer actually points to — every object would render identically. With virtual, C++ puts a lookup table called a vtable on every object. At runtime, shape->draw() asks the object: what kind are you? Then runs the right version. The render loop never changes. Each shape draws itself correctly. This runtime decision-making is called polymorphism.

A bug made it into one build: a bare Shape object was created directly with no real area() implementation, and the collision system silently treated it as having zero size. The fix was to make the contract impossible to skip. Writing virtual double area() const = 0; turns Shape into an abstract class. That = 0 means: this function has no body here — every concrete subclass must provide one. A plain Shape can no longer be created at all. Every object that enters the game world is forced to define its own area before it can exist. The compiler enforces the contract, and the bug becomes impossible.

When a level ends, Priya's engine deletes hundreds of Shape* objects to free memory. Some shapes own GPU texture handles that must be released, or the game leaks graphics memory on every level change. Without virtual ~Shape(), calling delete on a Shape* only runs Shape's destructor — even if the pointer actually points to a Circle. The Circle's cleanup never happens. The texture leaks silently. Adding virtual ~Shape() means the destructor follows the same vtable lookup as any virtual function: the right destructor runs, in the right order, every time.

The render loop does not know what it is drawing. It just calls draw(). That single fact is what "polymorphism" actually means in production code.

What we just learned

  • Inheritance — class Circle : public Shape means a circle is a kind of shape; it inherits all of Shape's members and can add its own
  • virtual function — uses a vtable to decide at runtime which version of a function to call, based on the actual object, not the pointer type
  • Polymorphism — one piece of code (the render loop) works correctly for many different types without knowing which type it holds
  • Abstract class — a class with at least one pure virtual (= 0) function; cannot be instantiated; forces every subclass to implement it
  • Virtual destructor — without it, deleting through a base pointer only runs the base destructor; derived cleanup and resources are silently lost

Also seen in the wild

GUI toolkitsA Widget base class lets a window loop call draw() on buttons, checkboxes, and sliders without knowing which one it holds — Priya's render loop in a different domain.
PaymentsA PaymentMethod base with CreditCard, PayPal, and UPI subclasses uses the same abstract-contract idea — just charging a customer instead of drawing a pixel.
Plugin systemsEditors like VS Code load unrelated plugins behind one common interface and must destroy each one safely through a base pointer — the virtual-destructor problem exactly.

Now combine the pieces into the complete use case
01
Shape hierarchy report

The complete program keeps the interface small: every shape can report its name and area, while each derived class owns its formula.

program.cpp - complete use case
#include <iostream>
#include <string>

class Shape {
public:
    virtual std::string name() const = 0;
    virtual double area() const = 0;
    virtual ~Shape() = default;
};

class Circle : public Shape {
    double radius;
public:
    explicit Circle(double r) : radius(r) {}
    std::string name() const override { return "Circle"; }
    double area() const override { return 3.14159 * radius * radius; }
};

class Rectangle : public Shape {
    double width, height;
public:
    Rectangle(double w, double h) : width(w), height(h) {}
    std::string name() const override { return "Rectangle"; }
    double area() const override { return width * height; }
};

void printReport(const Shape& shape) {
    std::cout << shape.name() << " area: " << shape.area() << std::endl;
}

int main() {
    Circle circle(2);
    Rectangle rectangle(3, 4);
    printReport(circle);
    printReport(rectangle);
}
Expected outputCircle area: 12.5664 Rectangle area: 12

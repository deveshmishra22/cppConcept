Polymorphism / Module 2

Inheritance & Polymorphism

Extend the banking-system thinking from Module 1 into families of related types. We will start with code reuse, then see why virtual functions are needed when one interface must work with many concrete objects.

Day: 2 of 6Topics: 4Case study: Shape hierarchyRepo folder: 08-ClassesandObjects/

Inheritance expresses an intentional relationship: a derived type is a more specific form of a base type.

WHY

Why share a common interface?

Suppose a graphics system needs circles, rectangles, and triangles. They all have a position and a way to describe themselves, but each shape stores different details. Inheritance lets shared behavior live in one base type while derived classes add their own behavior.

Public inheritance should communicate an honest “is-a” relationship. It is not just a shortcut for copying code.

WHAT

Base and derived syntax

The colon introduces the base class: class Circle : public Shape. Public inheritance keeps the base public interface public on the derived object. A derived constructor calls the base constructor before its own body runs.

inheritancecls.cpp
#include <iostream>

class Shape {
public:
    void describe() const { std::cout << "A drawable shape\n"; }
};

class Circle : public Shape {
public:
    void drawCircle() const { std::cout << "Drawing a circle\n"; }
};

int main() {
    Circle circle;
    circle.describe();
    circle.drawCircle();
}

Run the repository example

  1. Open 08-ClassesandObjects/inheritancecls.cpp.
  2. Compile with g++ -std=c++17 inheritancecls.cpp -o inheritance_demo.
  3. Run inheritance_demo.exe on Windows or ./inheritance_demo on Linux/macOS.

Inheritance alone reuses members. Polymorphism lets one base interface select the correct derived behavior at runtime.

WHY

Why a non-virtual function is not enough

If a Shape* points to a Circle, the compiler otherwise chooses the function based on the pointer's declared type. That is static binding. A virtual function asks C++ to choose the override based on the object that is actually there. This is dynamic binding.

HOW

Call through a base reference

polymorphismcls.cpp
#include <iostream>

class Shape {
public:
    virtual void draw() const { std::cout << "Generic shape\n"; }
    virtual ~Shape() = default;
};

class Circle : public Shape {
public:
    void draw() const override { std::cout << "Circle\n"; }
};

int main() {
    Circle circle;
    Shape& shape = circle;
    shape.draw();
}

override asks the compiler to check that the derived function really overrides a virtual base function. Use it whenever you intend overriding.

An abstract base class defines a contract but cannot be created directly.

WHAT

Pure virtual functions

Writing virtual double area() const = 0; makes the function pure virtual. Any concrete derived class must implement it before objects can be created. The base class becomes an interface-like contract for the rest of the program.

purevirtual-interfaces.cpp
class Shape {
public:
    virtual double area() const = 0;
    virtual ~Shape() = default;
};

class Rectangle : public Shape {
    double width;
    double height;
public:
    Rectangle(double w, double h) : width(w), height(h) {}
    double area() const override { return width * height; }
};
Design check: if a caller only needs to ask a shape for its area, it should depend on the Shape interface rather than know every future shape class.

A polymorphic base class needs a virtual destructor when objects may be destroyed through a base pointer.

WHY

Why virtual destruction matters

Shape* shape = new Circle; stores a derived object behind a base pointer. With a virtual destructor, delete shape runs the derived cleanup first and then the base cleanup. Without it, deleting through the base pointer is unsafe.

A vtable is an implementation technique commonly used to support virtual dispatch. Treat it as a useful mental model, not as a promise about one compiler's exact memory layout.

  1. Run virtualdestructor.cpp and observe destructor order.
  2. Read vtablemechanism.cpp after the behavior is clear.
  3. Compare the pure interface in purevirtual-interfaces.cpp.
🎬 Story Mode

One screen, many shapes

Picture this: you have just joined the rendering team at Nimbus Games. The current build's canvas needs to draw circles, rectangles, and — next sprint — triangles, all on the same frame, all needing a hitbox for collision. The lead engineer refuses to let the render loop know the concrete type of a single object it draws. This module is how that refusal becomes working code.

ACT 1

Every shape is a Shape first

Circles and rectangles clearly aren't the same thing, but they share a real relationship: both have a position, both get drawn, both belong on the same canvas. Rather than writing three unrelated structs, you give every on-screen object a common Shape base. class Circle : public Shape is Nimbus Games saying, honestly, "a circle is a kind of shape" — not just borrowing code to save typing.

ACT 2

The render loop that doesn't need to know

The renderer holds a list of Shape* — hundreds of objects per frame, mixed circles and rectangles, added and removed as the level plays. It calls shape->draw() once, in one loop, for every one of them. Without virtual, that call would always run Shape::draw() and every object on screen would render identically. With it, each object draws itself correctly — the renderer never needs an if (isCircle) anywhere in sight.

ACT 3

No object gets to skip the contract

A bug slips into a build: someone creates a bare Shape directly, forgets to give it a real area(), and the collision system silently treats it as having zero size. The lead engineer's fix is to make the contract impossible to dodge — virtual double area() const = 0; makes Shape abstract. Nobody can create a plain Shape again; every concrete object entering the game world is forced to define its own area before it can exist at all.

ACT 4

Unloading a level without leaking a frame

When a player finishes a level, Nimbus Games deletes hundreds of Shape* in one sweep to free memory before the next level loads. Some of those shapes own a texture handle that must be released, or the game leaks GPU memory every single level. Without a virtual ~Shape(), delete shape would only ever run the base destructor — the derived cleanup, and the texture, would silently never happen.

The compiler doesn't know it's rendering a game. It just knows it's holding a Shape, and calling the right function anyway — that's the entire trick behind every polymorphic renderer you've ever played.

Also seen in the wild

GUI toolkitsA Widget base class lets a window loop call draw() on buttons, checkboxes, and sliders without knowing which one it's holding — the same renderer pattern as Act 2.
PaymentsA PaymentMethod interface with CreditCard, PayPal, and UPI implementations is the same abstract-contract idea from Act 3, just charging a customer instead of drawing a pixel.
Plugin systemsEditors like VS Code load unrelated plugins behind one common interface, and must destroy each one safely through a base pointer — Act 4's exact problem.

class Shape {

        std::cout << "Shape\n";

class Circle : public Shape {

    circle.show();

Step 2Call derived behavior through the base

Change the call site to use a Shape reference.

step2_dispatch.cpp
#include <iostream>
class Shape {
public:
    virtual void show() const {
        std::cout << "Shape\n";
    }
};

class Circle : public Shape {
public:
    void show() const override {
        std::cout << "Circle\n";
    }
};

class Rectangle : public Shape {
public:
    void show() const override {
        std::cout << "Rectangle\n";
    }
};

void printShape(const Shape& shape) {
    shape.show();
}

int main() {
    Circle circle;
    Rectangle rectangle;
    printShape(circle);
    printShape(rectangle);
}

Run: g++ -std=c++17 step2_dispatch.cpp -o step2, then step2.exe or ./step2.

See: Circle then Rectangle

Step 3Make the contract abstract

Replace the generic implementation with a pure virtual function.

step3_area.cpp
#include <iostream>
class Shape {
public:
    virtual double area() const = 0;
    virtual ~Shape() = default;
};

class Rectangle : public Shape {
    double width;
    double height;

public:
    Rectangle(double w, double h) : width(w), height(h) {}

    double area() const override {
        return width * height;
    }
};

int main() {
    Rectangle rectangle(3, 4);
    std::cout << rectangle.area() << std::endl;
}

Run: g++ -std=c++17 step3_area.cpp -o step3, then step3.exe or ./step3.

Now combine the pieces into the complete use case
01
Shape hierarchy report

The complete program keeps the interface small: every shape can report its name and area, while each derived class owns its formula.

program.cpp - complete use case
#include <iostream>
#include <string>

class Shape {
public:
    virtual std::string name() const = 0;
    virtual double area() const = 0;
    virtual ~Shape() = default;
};

class Circle : public Shape {
    double radius;
public:
    explicit Circle(double r) : radius(r) {}
    std::string name() const override { return "Circle"; }
    double area() const override { return 3.14159 * radius * radius; }
};

class Rectangle : public Shape {
    double width, height;
public:
    Rectangle(double w, double h) : width(w), height(h) {}
    std::string name() const override { return "Rectangle"; }
    double area() const override { return width * height; }
};

void printReport(const Shape& shape) {
    std::cout << shape.name() << " area: " << shape.area() << std::endl;
}

int main() {
    Circle circle(2);
    Rectangle rectangle(3, 4);
    printReport(circle);
    printReport(rectangle);
}

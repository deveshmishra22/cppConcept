Robustness / Module 4

Exception Handling & Robustness

When a function cannot complete its job, C++ exceptions propagate the failure automatically — no silent return codes, no forgotten checks. RAII guarantees resources are released even when exceptions interrupt the flow.

Day: 3 of 6Topics: 4 + Story ModeCase study: Robust payment processorRepo folder: 10-ExceptionHandling/

An exception separates the normal code path from the error path — and unlike a return code, it cannot be accidentally ignored.

WHY

The return-code trap

Before exceptions, functions signalled failure by returning a special value — -1 for error, 0 for not-found, NULL for no result. The compiler never forces you to check, so one forgotten if-statement lets the program silently proceed in a broken state, perhaps corrupting data or crashing twenty calls later at a location that has nothing to do with the actual bug.

C++ exceptions offer three guarantees that error codes don't. First, an unhandled exception terminates the program rather than silently continuing. Second, the normal code path and the error path are visually separated — the try block is the optimistic scenario, the catch block is the failure handler. Third, when an exception propagates out of a function, every local object's destructor is called in reverse order — this is stack unwinding, and it is what makes the RAII pattern in Topic 4 safe.

WHAT

try, throw, and catch defined

  • try — marks a block of code where a throw might occur. Execution enters the block and runs until it completes normally or a throw is reached.
  • throw expression — immediately exits the current function and every calling function on the call stack until a matching catch is found. Local object destructors run as each frame exits (stack unwinding). If no catch matches anywhere, std::terminate() is called and the program aborts.
  • catch (Type& name) — handles exceptions of the specified type. Only runs when a matching throw occurred inside the corresponding try. catch (...) catches any type but provides no access to the exception object.
  • Key guarantee: code inside the try block after the throw site does not run — execution jumps directly to the matching catch. Code after the entire try/catch construct runs normally whether the exception was caught or not.
HOW

A safe division with exception handling

Adapted from 10-ExceptionHandling/Prog1.cpp in the course repo — notice how the normal output (5) and the error message appear in separate code paths, and the program survives both:

step1_trycatch.cpp
#include <iostream>
#include <stdexcept>

double divide(double numerator, double denominator) {
    if (denominator == 0.0)
        throw std::runtime_error("Division by zero");
    return numerator / denominator;
}

int main() {
    try {
        std::cout << divide(10, 2) << "\n";    // prints 5
        std::cout << divide(10, 0) << "\n";    // throws here
        std::cout << "This line never runs\n"; // skipped
    }
    catch (const std::runtime_error& e) {
        std::cout << "Caught: " << e.what() << "\n";
    }
    std::cout << "Program continues safely\n";
}
Expected output5 Caught: Division by zero Program continues safely

Different failures carry different information. Multiple catch clauses let each error type reach the handler that knows what to do with it.

WHY

One catch-all loses context

A catch(...) clause catches everything but gives you nothing to work with — you cannot call .what(), you cannot report which rule was violated, you cannot make a recovery decision. Typed exceptions exist so each class of failure carries its own context and reaches code that specifically understands it.

A missing file is not the same as an out-of-range index, and the correct response is different. Typed catch clauses make that distinction explicit in the code instead of hiding it behind a generic error message.

WHAT

The std::exception hierarchy

  • std::exception — the common base class in <exception>. Provides virtual const char* what() const noexcept. Your own custom exceptions should inherit from it.
  • std::runtime_error — for errors detectable only at runtime: file not found, network timeout, format mismatch. Constructor takes a string message.
  • std::logic_error — for programming bugs: invalid argument, precondition violation. Should indicate the caller did something wrong.
  • std::invalid_argument — derived from logic_error; an argument value that makes no sense for the function.
  • std::out_of_range — derived from logic_error; a value outside an acceptable range.
  • Catch order matters: clauses are tested top-to-bottom, first match wins. Put specific types before general ones — catch(std::out_of_range&) before catch(std::logic_error&) before catch(std::exception&).
HOW

Multiple catch clauses in action

The same try block, three different outcomes depending on which exception fires:

step2_catch_types.cpp
#include <iostream>
#include <stdexcept>

void validateAge(int age) {
    if (age < 0)
        throw std::invalid_argument("Age cannot be negative");
    if (age > 150)
        throw std::out_of_range("Age exceeds known human lifespan");
    std::cout << "Valid age: " << age << "\n";
}

int main() {
    int testAges[] = {25, -3, 200};
    for (int age : testAges) {
        try {
            validateAge(age);
        }
        catch (const std::invalid_argument& e) {
            std::cout << "Validation error: " << e.what() << "\n";
        }
        catch (const std::out_of_range& e) {
            std::cout << "Range error: " << e.what() << "\n";
        }
        catch (const std::exception& e) {
            std::cout << "Unexpected: " << e.what() << "\n";
        }
    }
}
Expected outputValid age: 25 Validation error: Age cannot be negative Range error: Age exceeds known human lifespan

Run it and experiment

  1. Compile: g++ -std=c++17 step2_catch_types.cpp -o step2, run.
  2. Experiment 1: Move catch(std::exception&) to be the first catch clause. It now catches everything — the more specific handlers below never run. The compiler doesn't warn you; the order is silently wrong.
  3. Experiment 2: Throw a raw int from validateAge (throw 42;) and add catch(int e). Non-exception types can be thrown, but they don't carry a what() message — which is exactly why the std::exception hierarchy exists.
Reference: cppreference: std::exception — the full standard exception hierarchy and their intended usage.

Standard exceptions report what went wrong. Custom exceptions also report the domain context — which account, which amount, which rule was violated.

WHY

What a string message can't tell you

When a withdrawal fails, the message "Insufficient funds" tells the catcher something happened. But it doesn't tell the catcher the balance, the requested amount, or the account ID — information that recovery code, audit logs, and user-facing messages need. Encoding context into a string and parsing it back at the catch site is fragile. A custom exception class stores each piece of context as a typed member, making it available directly without string parsing.

WHAT

Inheriting from std::exception

  • Inherit publicly from std::exception or a more specific standard class like std::runtime_error.
  • Override what() const noexcept to return const char* — a pointer to a string that lives at least as long as the exception object. Use a std::string member and return .c_str().
  • Mark what() as noexcept — it must not throw (it may be called during stack unwinding where a new exception would cause immediate termination).
  • Store domain context as typed members in the constructor — the catcher can access them directly without parsing the message string.

From the course repo: 10-ExceptionHandling/customexceptionProgram.cpp shows the same pattern applied to a bank withdrawal scenario.

HOW

A custom exception with typed context fields

step3_custom_exception.cpp
#include <iostream>
#include <exception>
#include <string>

class InsufficientFundsError : public std::exception {
    std::string message_;
    double balance_;
    double requested_;
public:
    InsufficientFundsError(double balance, double requested)
        : balance_(balance), requested_(requested) {
        message_ = "Need " + std::to_string(requested) +
                   ", only " + std::to_string(balance) + " available";
    }

    const char* what() const noexcept override { return message_.c_str(); }
    double balance()   const { return balance_;   }
    double requested() const { return requested_; }
};

void withdraw(double& balance, double amount) {
    if (amount <= 0)
        throw std::invalid_argument("Withdrawal amount must be positive");
    if (amount > balance)
        throw InsufficientFundsError(balance, amount);
    balance -= amount;
    std::cout << "Withdrawn: " << amount
              << "  |  Remaining: " << balance << "\n";
}

int main() {
    double balance = 500.0;
    try {
        withdraw(balance, 200.0);   // succeeds
        withdraw(balance, 400.0);   // throws InsufficientFundsError
    }
    catch (const InsufficientFundsError& e) {
        std::cout << "Transaction failed: " << e.what() << "\n";
        std::cout << "Shortfall: " << (e.requested() - e.balance()) << "\n";
    }
    catch (const std::invalid_argument& e) {
        std::cout << "Bad request: " << e.what() << "\n";
    }
}
Expected outputWithdrawn: 200 | Remaining: 300 Transaction failed: Need 400.000000, only 300.000000 available Shortfall: 100

Run it and experiment

  1. Compile: g++ -std=c++17 step3_custom_exception.cpp -o step3, run.
  2. Experiment 1: Add an accountId string member to InsufficientFundsError and pass it in the constructor — the catcher can then log exactly which account triggered the error without parsing the message.
  3. Experiment 2: Call withdraw(balance, -50.0) to trigger the invalid_argument path — the second catch clause fires instead.
  4. Experiment 3: Inherit from std::runtime_error instead of std::exception directly — pass the message string to std::runtime_error::runtime_error() in the initialiser list and remove the manual message_ member and what() override.

RAII (Resource Acquisition Is Initialization) is the pattern that makes exception-safe C++ possible — without a finally block in sight.

WHY

The gap between acquire and release

In languages with finally blocks, you write: acquire the resource in try, release it in finally. In C++, there is no finally. If an exception fires between fopen() and fclose(), the file never closes. Adding every resource to every catch block becomes unmaintainable as functions grow. And if you add a new early-return path, you'll forget to add the cleanup there too.

RAII closes this gap permanently: tie the resource's lifetime to an object's lifetime. The constructor acquires; the destructor releases. Since destructors always run when an object goes out of scope — including during stack unwinding from an exception — the resource is always released. You write the cleanup once, in one place, and it works for every exit path.

WHAT

RAII defined and standard RAII types

  • RAII — Resource Acquisition Is Initialization. The invariant: every resource (file handle, mutex lock, network socket, heap memory) is owned by an object. Constructor acquires; destructor releases. The object's lifetime is the resource's lifetime.
  • Why it works with exceptions: when an exception unwinds the stack, every local object's destructor runs in reverse-construction order. An RAII wrapper's destructor runs just like any other — regardless of whether the scope exited normally or via an exception.
  • std::ifstream / std::ofstream — RAII file handles. The file closes when the stream object is destroyed. From the course repo: 11-FStream/raii.cpp shows this pattern.
  • std::unique_ptr<T> — RAII heap memory. The pointed-to object is deleted when the pointer goes out of scope.
  • std::lock_guard<Mutex> — RAII mutex lock. The mutex is released when the guard is destroyed — even if an exception fires inside the locked section.
  • When to write your own: wrap any C API handle (socket fd, database connection, OS resource) that requires explicit cleanup into a class with acquire-in-constructor, release-in-destructor.
HOW

A RAII FileReader that always closes

The FileReader class guarantees its file handle closes whether the function returns normally, throws an exception, or the program exits — because the destructor always runs:

step4_raii.cpp
#include <iostream>
#include <fstream>
#include <stdexcept>
#include <string>

class FileReader {
    std::ifstream file_;
    std::string   path_;
public:
    explicit FileReader(const std::string& path) : path_(path), file_(path) {
        if (!file_.is_open())
            throw std::runtime_error("Cannot open: " + path);
        std::cout << "[FileReader] Opened: " << path << "\n";
    }

    ~FileReader() {
        // Runs whether the scope exits normally or via exception
        std::cout << "[FileReader] Closed: " << path_ << "\n";
    }

    std::string readLine() {
        std::string line;
        if (!std::getline(file_, line))
            throw std::runtime_error("No more lines in: " + path_);
        return line;
    }
};

int main() {
    // Scenario 1: file does not exist — constructor throws,
    //             destructor does NOT run (resource never acquired)
    std::cout << "--- Scenario 1: missing file ---\n";
    try {
        FileReader reader("nonexistent.txt");
        std::cout << reader.readLine() << "\n";
    }
    catch (const std::runtime_error& e) {
        std::cout << "Error: " << e.what() << "\n";
    }

    // Scenario 2: create file, then read it
    std::cout << "\n--- Scenario 2: existing file ---\n";
    {
        std::ofstream out("sample.txt");
        out << "Hello from RAII\nSecond line\n";
    }  // out destroyed here — file flushed and closed automatically

    try {
        FileReader reader("sample.txt");
        std::cout << reader.readLine() << "\n";
    }  // reader destroyed here — file closed automatically
    catch (const std::runtime_error& e) {
        std::cout << "Error: " << e.what() << "\n";
    }
}
Expected output--- Scenario 1: missing file --- Error: Cannot open: nonexistent.txt --- Scenario 2: existing file --- [FileReader] Opened: sample.txt Hello from RAII [FileReader] Closed: sample.txt

🎬 Story Mode

The overnight job that woke everyone up

Every night at 2 AM, Nimbus Payments ran a batch job that processed thousands of withdrawals. For six months it worked. Then one night it crashed halfway through — no rollback, no error log, just a half-processed batch and a panicked 6 AM phone call. Half the transactions had gone through and half had not, and nobody could tell which half. This module is how the team made sure that morning never happened again.

The original batch processor returned error codes — when it remembered to. When a transaction hit a divide-by-zero inside an interest calculation, the code just kept running with garbage data and produced silently wrong results that nobody noticed for three days. The fix was to wrap the processing loop in a try block. An exception is an object that gets thrown when something goes wrong and travels up the call stack until something catches it. catch (const std::runtime_error& e) is that something. The happy path and the failure path are now in separate blocks. The bad transaction logs an error and the batch moves on to the next one — nothing silently corrupts.

But not every failure should be handled the same way. A missing account number is a data problem — skip and flag for review. A network timeout is a temporary problem — retry. A disk-full error is a system problem — stop everything immediately. Three different problems need three different catch clauses. C++ tests them in order from top to bottom and runs the first one that matches. This is called catching by type. The key rule: specific exception types must come before general ones. If you put catch (std::exception&) first, it matches everything and the specific handlers below it never run.

After the fix, the overnight log showed: runtime_error: Insufficient funds. At 3 AM that is useless. Which account? Short by how much? Nobody knew without digging through the database by hand. The team built InsufficientFundsError — a custom exception that inherits from std::exception and carries typed fields: account ID, current balance, requested amount. The what() function returns a human-readable message. The catch block now has everything it needs to write a complete audit entry and send the exact customer notification — without parsing strings or storing state in globals.

There was still one more problem. Every transaction opened a database connection and closed it before returning — except when an exception fired between open and close. Over a long weekend, 200 transactions had thrown mid-processing and 200 connections were still sitting open. The pool exhausted. The fix: a DatabaseConnection class whose constructor opens the connection and whose destructor closes it. This pattern is called RAII — Resource Acquisition Is Initialization. Tie the lifetime of a resource to the lifetime of an object. The destructor runs whether the function returned normally, threw an exception, or was interrupted. The connection always closes. The pool never exhausts again.

An exception is not an error message. It is a signal that travels up the call stack until someone is ready to handle it. RAII makes sure all the resources below it close cleanly on the way out.

What we just learned

  • Exception — an object thrown when something goes wrong; travels up the call stack until a matching catch handles it
  • try / catch — try wraps the code that might fail; catch handles specific error types; separates the happy path from failure handling
  • Catching by type — C++ tests catch clauses top to bottom; specific types must come before general ones or the general clause swallows everything
  • Custom exception — a class inheriting from std::exception with typed context fields and what() overridden for a readable message
  • RAII — Resource Acquisition Is Initialization; acquire in the constructor, release in the destructor; the resource closes whether the function returns normally or throws

Also seen in the wild

File systemsstd::ifstream closes its file handle in the destructor — RAII shipped as a standard library type you use every day.
Concurrencystd::lock_guard acquires a mutex on construction and releases on destruction — prevents deadlocks the same way DatabaseConnection prevents exhausted pools.
Graphics APIsVulkan and DirectX resource wrappers in game engines follow RAII — GPU handles acquired in constructor, released in destructor, regardless of how rendering exits.
Web serversHTTP connection objects wrap socket file descriptors in RAII wrappers — the socket closes when the object is destroyed, even if request handling throws.

double divide(double a, double b) {

Step 3Custom exception with context

The catcher gets typed fields, not just a string.

step3_custom_exception.cpp
#include <iostream>
#include <exception>
#include <string>

class InsufficientFundsError : public std::exception {
    std::string msg_;
    double shortfall_;
public:
    InsufficientFundsError(double bal, double req)
        : shortfall_(req - bal),
          msg_("Short by " + std::to_string(req - bal)) {}
    const char* what() const noexcept override { return msg_.c_str(); }
    double shortfall() const { return shortfall_; }
};

void withdraw(double& bal, double amt) {
    if (amt > bal) throw InsufficientFundsError(bal, amt);
    bal -= amt;
    std::cout << "OK, balance: " << bal << "\n";
}
int main() {
    double bal = 300.0;
    try { withdraw(bal, 500.0); }
    catch (const InsufficientFundsError& e) {
        std::cout << e.what() << " (shortfall: " << e.shortfall() << ")\n";
    }
}

Run: g++ -std=c++17 step3_custom_exception.cpp -o step3

Robust payment batch processor

One loop, multiple transaction types, typed exceptions, program never crashes.

program.cpp — complete use case
#include <iostream>
#include <stdexcept>
#include <vector>
#include <string>

class PaymentError : public std::exception {
    std::string msg_;
public:
    PaymentError(const std::string& account, double balance, double amount)
        : msg_("Account " + account + ": need " + std::to_string(amount) +
               ", have " + std::to_string(balance)) {}
    const char* what() const noexcept override { return msg_.c_str(); }
};

struct Transaction {
    std::string accountId;
    double balance;
    double amount;
};

void processTransaction(const Transaction& t) {
    if (t.amount <= 0)
        throw std::invalid_argument("Amount must be positive");
    if (t.amount > t.balance)
        throw PaymentError(t.accountId, t.balance, t.amount);
    std::cout << "[OK]   " << t.accountId << " paid " << t.amount
              << "  |  balance: " << (t.balance - t.amount) << "\n";
}

int main() {
    std::vector<Transaction> batch = {
        {"ACC001", 500.0,   200.0},
        {"ACC002", 100.0,   300.0},
        {"ACC003", 750.0,   -50.0},
        {"ACC004", 1000.0,  400.0},
    };

    int ok = 0, failed = 0;
    for (const auto& t : batch) {
        try {
            processTransaction(t);
            ++ok;
        }
        catch (const PaymentError& e) {
            std::cout << "[FAIL] Insufficient — " << e.what() << "\n";
            ++failed;
        }
        catch (const std::invalid_argument& e) {
            std::cout << "[FAIL] Invalid — " << e.what() << "\n";
            ++failed;
        }
    }
    std::cout << "\nBatch done. OK: " << ok << "  Failed: " << failed << "\n";
}
Expected output[OK] ACC001 paid 200 | balance: 300 [FAIL] Insufficient — Account ACC002: need 300.000000, have 100.000000 [FAIL] Invalid — Amount must be positive [OK] ACC004 paid 400 | balance: 600 Batch done. OK: 2 Failed: 2

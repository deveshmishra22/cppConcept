Foundation Enhancer

Before we write a single class, we need to agree on why C++ looks the way it does. This module resets the mental model — from "functions acting on data" to "objects that own their data" — so every keyword you type from Module 1 onward has a reason behind it.

Day: 1 of 6 Topics: 7 Type: Conceptual + 1 hands-on check Repo folder: root files & 01-Structs/

Before classes, students need to know what a C++ file is, what the compiler does with it, and what each line of the first program means.

WHY

What happens when C++ code runs?

A .cpp file is human-readable source code. The toolchain turns it into a program in stages:

  1. Preprocess: expands lines such as #include <iostream>.
  2. Compile: checks C++ syntax and translates each source file into machine-oriented object code.
  3. Link: combines object code with required library code and creates an executable.
  4. Run: the operating system loads the executable and calls main().

VS Code is the editor where we write and inspect code. It is not the compiler by itself. We also need a compiler toolchain and a terminal command to build the file.

WHAT

C++ compared with C# and other managed languages

If you know C#, the difference is useful rather than scary. A C# file is compiled into CIL (also called MSIL), and the CLR loads that intermediate code, verifies it, and usually JIT-compiles methods to machine code while the program runs. The runtime supplies services such as garbage collection.

C++ normally follows a more direct path: the compiler turns each source file into native object code, the linker joins it with libraries, and the operating system loads the resulting executable. There is no required CLR between your program and the operating system, so you choose more of the memory, binary, and deployment details. That extra control is why C++ is common in systems software, but the edit-compile-run loop is still straightforward.

Two execution paths
C# / .NET:  Program.cs
             -> C# compiler
             -> CIL / MSIL assembly
             -> CLR + JIT
             -> machine code at runtime

C++:       program.cpp
             -> preprocessor
             -> C++ compiler
             -> object file
             -> linker + libraries
             -> native executable
             -> operating system loader
Connection: C# developers already know the most important workflow idea: source code is transformed by tools before it executes. C++ changes where that transformation happens and who owns more of the runtime details; it does not require learning programming from zero.
WHAT

Tools required for this course

  • VS Code: editor, integrated terminal, and optional Microsoft C/C++ extension for completion and error hints.
  • GCC / g++: the GNU C++ compiler. On Windows, install a MinGW-w64 distribution such as MSYS2; on Ubuntu use sudo apt install g++; on macOS use Apple Clang via xcode-select --install.
  • MSVC: Microsoft's compiler, installed with Visual Studio or Build Tools. Use the Developer Command Prompt and the cl command.
  • Clang: an LLVM compiler available as clang++. It follows the same edit, compile, run cycle.
  • CMake: a build-system tool we will introduce when projects need more than one source file. It is not required for this first exercise.

Check which compiler is installed

  1. GCC: g++ --version
  2. Clang: clang++ --version
  3. MSVC: open a Developer Command Prompt and run cl
  4. Use one available compiler consistently while learning. The examples below use g++.
WHAT

Read the first C++ program line by line

#include <iostream> makes declarations for standard input and output available. The angle brackets mean the compiler searches its standard include locations.

std is the namespace owned by the C++ standard library. cout, cin, and endl are names provided by that library. The std:: prefix says exactly where each name comes from; it is not part of the variable's name.

std::cout writes to the console, std::cin reads from keyboard input, and std::endl inserts a new line and flushes the output buffer. They are ready-made library objects and manipulators, but we can write our own functions and namespace names alongside them.

hello.cpp
#include <iostream>
#include <string>

int main() {
    std::cout << "Enter your name: ";
    std::string name;
    std::cin >> name;
    std::cout << "Hello, " << name << std::endl;
    return 0;
}
Notice: each standard-library type or facility should have its own include. This is why the example includes both <iostream> and <string>.
HOW

Namespaces and familiar ideas in other languages

Namespaces prevent two libraries from using the same short name without conflict. We can create one ourselves:

namespaces.cpp
#include <iostream>

namespace training {
    void hello() { std::cout << "Hello from training" << std::endl; }
}

int main() {
    training::hello();
    return 0;
}

The same organizing idea appears elsewhere: Python uses modules such as math.sqrt, Java uses packages such as java.util.List, and JavaScript uses imports such as console.log from a module. C++ uses namespace::name.

You may write using namespace std; in a tiny learning file, but avoid putting it in shared headers or large programs because it imports many short names and can create collisions. Prefer std::cout while learning where each name came from.

Compile and run the first file

  1. From a terminal, create and enter a folder: mkdir cpp-first-run then cd cpp-first-run. In VS Code you can open it with code ..
  2. Save the file in VS Code as program.cpp.
  3. GCC: g++ -std=c++17 program.cpp -o program, then Windows program.exe or macOS/Linux ./program.
  4. Clang: clang++ -std=c++17 program.cpp -o program, then run the same executable command.
  5. MSVC: cl /std:c++17 program.cpp, then run program.exe.
  6. When you edit the file, compile again. The executable does not update until a successful build finishes.

C++ wasn't invented to replace C — it was invented because one engineer, maintaining large C systems at Bell Labs, kept hitting the same wall.

WHY

Why C wasn't enough for growing systems

By the early 1980s, Bjarne Stroustrup was building simulation software in C and repeatedly ran into the same problems every large C codebase eventually hits:

  • Data and the functions that operate on it live apart. A struct Employee and the twenty functions that touch it are scattered across files, with nothing stopping unrelated code from reaching in and corrupting the data.
  • No safe way to reuse and extend behaviour. If ten teams need a "manager" that behaves like an "employee" plus a bit more, C gives you copy-paste, not a language mechanism for "is-a-kind-of".
  • Manual memory bookkeeping, with no cleanup guarantee. Every malloc needs a matching free, tracked entirely by discipline — one missed path and you leak memory in production.

C++ started life literally as "C with Classes" — Stroustrup's answer was to keep C's performance and low-level control, but let programmers group data with behaviour, model relationships, and let the compiler enforce some of the discipline humans kept forgetting.

WHAT

What C++ actually adds on top of C

C++ is (almost entirely) a superset of C — most valid C compiles as C++ — plus a set of additions that matter for this course:

  • Classes & objects — bundling data with the functions that act on it (Module 1).
  • Inheritance & polymorphism — modelling "is-a" relationships and runtime behaviour (Module 2).
  • Templates — writing logic once for any type, resolved at compile time (Module 5).
  • Exceptions — a structured way to signal and handle errors, instead of checking a return code after every call.
  • The Standard Template Library (STL) — battle-tested containers and algorithms you don't have to write yourself (Module 6).

Enterprise systems — trading engines, telecom switches, game engines, embedded and OS-level code — still lean on C++ today for exactly the reason Stroustrup designed it: you get structure without giving up the raw performance and memory control that C offers.

HOW

Confirm your compiler and C++ standard

Every C++ compiler defines a special macro, __cplusplus, whose value tells you which language standard you're actually compiling against (C++11, C++14, C++17, C++20...). This matters because several features in this course — lambdas, smart pointers, auto — depend on the standard being used.

cppversioncheck.cpp 
#include <iostream>
using namespace std;

int main() {
    // __cplusplus is a predefined macro — the compiler fills in its
    // value based on which C++ standard you're compiling against.
    // 201703L means C++17, 201402L means C++14, and so on.
    cout << "C++ version: " << __cplusplus << endl;

    cin >> ws;   // consumes any stray whitespace left in the input buffer
    return 0;
}
Expected output (will vary by compiler/flags)C++ version: 201703

The single biggest shift moving from C to C++ isn't syntax — it's where you put the logic.

WHY

Why "who can change this data?" becomes a real question

In a purely procedural style, data structures are passive — any function, anywhere in the program, can reach in and modify a record. That's fine for a 200-line script. It stops being fine once fifteen developers are touching the same Employee struct across forty files: nobody can be sure which function last changed a field, or whether it did so safely.

Object-oriented programming's answer is to attach the data to the behaviour that's allowed to touch it. The object becomes the unit of change — and the unit you reason about, test, and reuse.

WHAT

Procedural vs OOP, defined

  • Procedural paradigm: the program is a sequence of functions/procedures. Data is typically passed into functions as arguments; there's no built-in link between a piece of data and the operations meant for it.
  • Object-oriented paradigm: the program is a set of objects, each bundling its own data (state) with the functions (methods) that operate on that data. Access can be restricted (Module 1's Access Specifiers), and objects can be extended through inheritance (Module 2).

Neither paradigm is "better" in the abstract — C++ actually lets you mix both. But for anything with meaningful state and lifetime (a bank account, a network connection, a UI widget), OOP tends to scale better as a codebase grows.

HOW

The same problem, two ways

Here's one small task — store a student's roll number and name, then print them — written both ways so you can see exactly what OOP changes.

procedural_style.cpp
#include <iostream>
using namespace std;

// Procedural style: data (rollNo, name) and behaviour (displayStudent)
// are completely separate. Any function in this file could modify
// rollNo or name directly — nothing stops it.
struct StudentData {
    int rollNo;
    string name;
};

void displayStudent(StudentData s) {
    cout << "Roll: " << s.rollNo << ", Name: " << s.name << endl;
}

int main() {
    StudentData s1;
    s1.rollNo = 101;
    s1.name = "Ravi";

    displayStudent(s1);   // we had to remember which function does this
    return 0;
}
oop_style.cpp
#include <iostream>
using namespace std;

// OOP style: the Student class owns both its data and the one
// function that's meant to touch it. rollNo/name are private —
// see Module 1's Access Specifiers for exactly what that buys us.
class Student {
private:
    int rollNo;
    string name;

public:
    void setDetails(int rollNo, string name) {
        this->rollNo = rollNo;
        this->name = name;
    }

    void display() {
        cout << "Roll: " << rollNo << ", Name: " << name << endl;
    }
};

int main() {
    Student s1;
    s1.setDetails(101, "Ravi");
    s1.display();          // the object knows how to display itself
    return 0;
}
Both programs printRoll: 101, Name: Ravi

⚡ Quick guide — try it yourself

  1. Save the two snippets as procedural_style.cpp and oop_style.cpp.
  2. Compile each: g++ procedural_style.cpp -o proc and g++ oop_style.cpp -o oop
  3. Run both and confirm they print the same result.
  4. Now try this on your own: add an age field to both versions. Notice how in oop_style.cpp you only touch the Student class, while in procedural_style.cpp you have to check every function that receives a StudentData.

Three habits carry over from C that quietly cause bugs in C++ if you don't unlearn them deliberately.

WHY

Why these three differences matter in practice

  • struct vs class: C programmers default to struct out of habit. In C++, that habit silently makes every member public — fine for a plain data bag, risky for anything meant to protect its state.
  • malloc/free vs new/delete: mixing them is undefined behaviour. malloc hands you raw, uninitialised memory — it never calls a constructor. free-ing an object created with new skips its destructor entirely.
  • return codes vs exceptions: traditional C checks an error code after every call. C++ can throw an exception at the point of failure and let it propagate to whoever is actually equipped to handle it (see Module 4).
WHAT

The rules, precisely

  • Default access: struct members are public by default; class members are private by default. That's the only hard difference — both can have constructors, methods, and inheritance in C++.
  • Memory allocation: new/delete call the constructor/destructor for you and are type-safe. malloc/free just reserve/release raw bytes — no constructor, no destructor, no type checking.
  • Error handling: C conventionally signals failure via a return value or errno, which the caller must remember to check. C++ exceptions unwind the stack automatically and can carry rich error context — at the cost of a small runtime overhead when actually thrown.
HOW

struct in C++ — still a full type, just public by default

This is the actual Person struct from the course repository — notice it has a member function, just like a class would.

01-Structs/Program1.cpp
#include <iostream>
using namespace std;

struct Person
{
    // No access specifier given -> these are public by default,
    // because this is a struct, not a class.
    string first_name;
    string last_name;
    int age;
    float salary;

    void introduce() {
        cout << "Hi, my name is " << first_name
             << " and I am " << age << " years old." << endl;
    }
};

int main()
{
    Person p1;
    cout << "Enter first name: ";
    cin >> p1.first_name;     // works because first_name is public
    cout << "Enter last name: ";
    cin >> p1.last_name;
    cout << "Enter age: ";
    cin >> p1.age;
    cout << "Enter salary: ";
    cin >> p1.salary;

    cout << "\nDisplaying Information." << endl;
    cout << "First Name: " << p1.first_name << endl;
    cout << "Last Name: " << p1.last_name << endl;
    cout << "Age: " << p1.age << endl;
    cout << "Salary: " << p1.salary;

    p1.introduce();
    return 0;
}

The same small requirement can be solved in both languages. The goal is not to declare one language better; it is to see how C++ evolves C's low-level control into stronger grouping, safer interfaces, and library-supported types.

One problemStore one student's name and score, then print whether the student passed. We will allocate the record dynamically so the memory-management difference is visible.
C version - student.c

C keeps a plain struct and separate functions. The caller manages the pointer and checks the allocation result.

student.c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

typedef struct {
    char name[40];
    int score;
} Student;

void set_student(Student* student, const char* name, int score) {
    strncpy(student->name, name, sizeof(student->name) - 1);
    student->name[sizeof(student->name) - 1] = '\0';
    student->score = score;
}

void print_result(const Student* student) {
    printf("%s scored %d: %s\n", student->name,
           student->score,
           student->score >= 50 ? "PASS" : "RETRY");
}

int main(void) {
    Student* student = malloc(sizeof *student);
    if (student == NULL) return 1;

    set_student(student, "Asha", 86);
    print_result(student);
    free(student);
    return 0;
}

Build: gcc -std=c11 student.c -o student_c

Run: Windows student_c.exe; Linux/macOS ./student_c

C++ version - student.cpp

C++ groups the data and operations in a class. The class protects its fields and gives callers a small public interface.

student.cpp
#include <iostream>
#include <string>

class Student {
private:
    std::string name;
    int score;

public:
    Student(const std::string& studentName, int studentScore)
        : name(studentName), score(studentScore) {}

    void printResult() const {
        std::cout << name << " scored " << score << ": "
                  << (score >= 50 ? "PASS" : "RETRY")
                  << std::endl;
    }
};

int main() {
    Student* student = new Student("Asha", 86);
    student->printResult();
    delete student;
    return 0;
}

Build: g++ -std=c++17 student.cpp -o student_cpp

Run: Windows student_cpp.exe; Linux/macOS ./student_cpp

Both programs produceAsha scored 86: PASS
WHAT

What changed and why it matters

  • Data and behavior: C keeps Student data in a struct and puts functions outside it. C++ puts printResult inside the class, so the object owns the behavior that understands its state.
  • Memory: C uses malloc and free; C++ uses new and delete in this teaching example. In production C++, prefer automatic lifetime or std::unique_ptr instead of owning a raw pointer.
  • Types: C uses a fixed character array and C string functions. C++ uses std::string, which manages its own character storage.
  • Access: C has no private: section in a struct. C++ classes default to private members, so callers cannot change score directly.
  • Syntax: -> still means access through a pointer in both examples. C++ adds constructors, member functions, access control, and standard-library abstractions around the same underlying machine resources.

Try the comparison yourself

  1. Change 86 to 42 in both files and rebuild both programs.
  2. In the C++ version, try writing student->score = 100; in main. Read the compiler error.
  3. In the C version, notice that the external function can access every field through the pointer.
  4. Keep the output the same while identifying which language feature makes each version different.
🎬 Story Mode

The firmware nobody wanted to touch

Arjun had worked at Nimbus Vending for three years. His job one afternoon: add a new premium machine type to the existing C firmware. He opened the codebase and found forty functions and eight global arrays — slot[8], price[8] — with nothing saying which function was allowed to touch which array. He changed one price, ran the build, and broke two machine types he had never touched. He told his manager: this code is not broken. It is just very easy to break by accident.

Before Arjun could even begin to fix anything, he had to be able to run the code. This sounds obvious, but a lot of beginners mix up three different things. An editor is just where you write text. A compiler — g++ or clang++ in C++ — reads that text and produces a binary file. The binary is what actually runs on the vending machine hardware. These are three separate tools. Getting comfortable with the compile command and the output file is the very first skill — not because it is interesting, but because nothing else works without it.

Arjun's manager asked the obvious question: why switch to C++ at all? Can't we keep the firmware in plain C? Arjun had one answer. C++ was invented by Bjarne Stroustrup in the 1980s specifically for large C codebases that hit exactly this wall. His early name for it was "C with Classes." The idea was not to replace C — the team's decades of C knowledge stay completely valid. The idea was to add one thing C does not have: a way to say that this data and these functions belong together in one named place.

That missing thing is the whole difference between procedural programming and object-oriented programming. In Arjun's firmware, slot[8] is just memory. Any function anywhere can walk up and change it — nobody owns it. In OOP you give data a home. A VendingMachine class holds its own slots and prices, and only the code inside that class can change them. The machine owns its own state. Nothing reaches in from outside without permission.

Arjun wrote the migration team a short list of concrete differences. In C, a struct is only fields — no rules about who reads or writes them. In C++, a class adds access control: you decide what is visible to the outside. malloc/free give way to constructors and destructors that run at the right time automatically. Return codes — the ones the team kept forgetting to check — give way to exceptions that callers cannot silently ignore. Every item on that list is a category of bug Nimbus had already shipped.

To make the argument concrete, Arjun built the same small record-keeping program twice: once in C with a struct and malloc, once in C++ with a class that protects its own data. Same output on screen, clearly different guarantees in code. His manager approved the rewrite the same afternoon.

C++ did not replace C's toolbox. It gave the same tools drawers, labels, and locks.

What we just learned

  • Toolchain — editor writes code, compiler turns it into a binary, the binary runs; three separate tools
  • C to C++ — C++ is C extended with classes; "C with Classes" was Stroustrup's original name; your C knowledge transfers completely
  • Procedural vs OOP — procedural separates data from functions; OOP puts data and the functions that own it together inside one class
  • class vs struct — a C++ class adds access control and member functions to what a plain C struct can do
  • Exceptions — unlike return codes, C++ exceptions cannot be silently ignored by the caller

Also seen in the wild

Automotive firmwareSafety-critical ECU codebases have made the same C-to-C++ move for the same encapsulation reasons Arjun described.
Apple/NeXTObjective-C took the opposite syntax path but solved the identical problem: adding OOP discipline on top of existing C code.
.NET / C#C# enforces access rules the same way — C++ just asks you to reason about it one layer closer to the hardware.

Understand the shape of the solution

Learner stores the data. printProgress owns the reporting behavior. main creates the record and calls the function. Notice how the data and behavior are still separate; Module 1 will show how a class can bring them together.

program.cpp · complete use case
#include <iostream>
#include <string>

struct Learner {
    std::string name;
    int completedTopics;
    int totalTopics;
};

void printProgress(const Learner& learner) {
    std::cout << learner.name << " completed "
              << learner.completedTopics << " of "
              << learner.totalTopics << " topics." << std::endl;

    if (learner.completedTopics == learner.totalTopics) {
        std::cout << "Status: ready for the next module." << std::endl;
    } else {
        std::cout << "Status: keep practising." << std::endl;
    }
}

int main() {
    Learner learner{"Asha", 3, 4};
    printProgress(learner);
    return 0;
}

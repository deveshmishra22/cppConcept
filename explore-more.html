Question 01PolymorphismRuntime dispatch

What is the real use of the virtual keyword?

WHY

What confusion does it solve?

Inheritance alone lets a child object be treated as a parent object, but a call through a parent type normally selects the parent version at compile time. The virtual keyword asks C++ to choose the override at runtime when the call is made through a base pointer or reference.

Simple rule: the object is created as a Dog, but the variable is a Animal*. Without virtual, the compiler uses the variable's type. With virtual, C++ follows the object's real type.
WHAT

Compile-time call versus runtime call

virtual_dispatch.cpp
#include <iostream>
using namespace std;

struct Animal {
    virtual void speak() const { cout << "Animal sound\n"; }
    virtual ~Animal() = default;
};

struct Dog : Animal {
    void speak() const override { cout << "Dog bark\n"; }
};

int main() {
    Dog dog;
    Animal* animal = &dog; // parent-typed pointer, child object
    animal->speak();      // virtual dispatch: Dog::speak()
}

The base pointer is the important part. If you call dog.speak() directly, there is no polymorphic decision to make. If you call through Animal* or Animal&, virtual enables runtime dispatch, commonly implemented with a vtable and vptr.

HOW

How to decide whether to use it

  • Use virtual when derived classes should provide different behavior through one base interface.
  • Add override in the child class so the compiler verifies that a real override exists.
  • Give a polymorphic base class a virtual destructor when objects may be deleted through a base pointer.
  • Do not add it merely because inheritance exists; use it when runtime behavior must vary by the actual object type.
Question 02Calling conventionsCricket demo

How should I understand 3_calling_conventionscricket-demo.cpp?

WHY

What problem do calling conventions solve?

A calling convention is the agreed rule between a caller and a function about how a function call works. It answers questions such as: where do arguments go, where does the return value go, who restores the stack, and which registers may be changed?

Cricket analogy: the caller is the batter sending the required information, the function is the bowler following the agreed delivery format, and the return value is the result of the ball. Both sides must follow the same rules or the play breaks.
WHAT

What the code is demonstrating

The demo is not showing a different C++ function body. It is showing that the compiler and platform ABI decide how the same call is represented at machine-code level. On modern 64-bit Windows, many older convention keywords are unified by the platform ABI, so the conceptual lesson is more important than expecting visibly different output.

calling_conventions_concept.cpp
#include <iostream>

int add(int first, int second) {
    return first + second;
}

int main() {
    // The compiler follows the platform ABI for passing these arguments.
    std::cout << add(10, 20) << "\n";
}
HOW

How to read the demo

  1. Find the function declaration and identify its parameters and return type.
  2. Find the call site: the caller prepares the arguments according to the ABI.
  3. At the machine-code level, arguments may use registers or the stack.
  4. The called function computes the result and returns it using the agreed return mechanism.
  5. On the same compiler and target, caller and callee automatically use the same rules; mismatches matter when crossing compiler, language, or library boundaries.

For ordinary application code, let the compiler choose the convention. The topic becomes especially relevant for operating-system APIs, C interoperability, callbacks, plugins, embedded systems, and performance-sensitive assembly interfaces.

Foundations / Module 1

C++ Basics

This module runs one case study end to end: a bank account. We'll build it up piece by piece — turning it into a class, locking down its data, giving it proper construction and cleanup, adding a shared counter, and finally letting one trusted class audit it — so every keyword below has a job to do inside a system you'd actually recognise.

Day: 1 of 6 Topics: 5 Case study: Banking system Repo folder: 08-ClassesandObjects/
// RUNNING CASE STUDY We're building BankAccount — a class that must never let its balance be corrupted from outside, must always start in a valid state, must know how many accounts exist bank-wide, and must let exactly one trusted class (a bank manager) audit its private data. Each tab below adds one capability.

A class is the blueprint. An object is one real account built from it.

WHY

Why bundle balance and behaviour together

Think about what a bank account actually needs to guarantee: nobody should be able to set the balance to an arbitrary number without going through deposit/withdraw logic. If balance is just a loose variable passed around functions (Module 0's procedural style), that guarantee is impossible to enforce — any function anywhere can assign to it directly. A class lets the account carry its own rules with it, wherever it goes.

WHAT

Class syntax, objects, and where they live in memory

A class is declared with the class keyword and a body of members (data + functions). An object is a concrete instance of that class. In C++, you choose where an object lives:

  • Stack allocation — BankAccount acc; — created and destroyed automatically when it goes out of scope.
  • Heap allocation — BankAccount* acc = new BankAccount(); — you control its lifetime, and you must call delete yourself when done, or it leaks.
HOW

A minimal BankAccount class, both ways

This mirrors a real pattern from the course repo (08-ClassesandObjects/c1.cpp), rebuilt around our case study:

bank_account_basic.cpp
#include <iostream>
using namespace std;

class BankAccount {
public:
    string owner;
    double balance;

    void deposit(double amount) {
        balance += amount;
        cout << owner << " deposited " << amount
             << ". New balance: " << balance << endl;
    }
};

int main() {
    BankAccount acc1;                     // stack allocation
    acc1.owner = "Ravi";
    acc1.balance = 1000;
    acc1.deposit(500);

    BankAccount* acc2 = new BankAccount(); // heap allocation
    acc2->owner = "Anita";
    acc2->balance = 2000;
    acc2->deposit(750);

    delete acc2;   // we allocated with new, so we must delete it ourselves
    return 0;
}
Expected outputRavi deposited 500. New balance: 1500 Anita deposited 750. New balance: 2750

⚡ Quick guide — try it yourself

  1. Save as bank_account_basic.cpp, compile: g++ -std=c++17 bank_account_basic.cpp -o bank1
  2. Run it: ./bank1
  3. Try this: remove the delete acc2; line, recompile, and run again — the program still works, but you've now leaked memory. Memory tools and profiling are planned for Module 7.

Notice balance is still public here — anyone can write acc1.balance = -99999; and the class can't stop them. That's exactly the gap Access Specifiers close next.

Now we close the gap the last tab ended on.

WHY

Why balance can't stay public

A public balance means any line of code, anywhere in a million-line codebase, can silently corrupt it — no logging, no validation, no way to trace who did it. Enterprise systems treat this as a design defect. The fix is to hide the data and expose only the operations that are allowed to change it.

WHAT

public, private, protected

  • public — accessible from anywhere the object is visible.
  • private — accessible only from inside the class's own member functions (and its friends — Tab 5). This is the default for class.
  • protected — like private, but also accessible to derived classes. You'll use this properly once inheritance is introduced in Module 2.

A common enterprise pattern: keep data private, and expose controlled public methods to read or change it — often called getters and setters, though good design keeps them meaningful (like deposit()) rather than a raw setBalance() that defeats the whole point.

HOW

Locking down BankAccount's balance

bank_account_private.cpp
#include <iostream>
using namespace std;

class BankAccount {
private:
    double balance;   // no code outside this class can touch balance directly

public:
    string owner;

    void deposit(double amount) {
        if (amount <= 0) {
            cout << "Deposit must be positive." << endl;
            return;
        }
        balance += amount;
    }

    void withdraw(double amount) {
        if (amount > balance) {
            cout << "Insufficient funds." << endl;
            return;
        }
        balance -= amount;
    }

    double getBalance() {
        return balance;   // the only way outside code can read balance
    }
};

int main() {
    BankAccount acc;
    acc.owner = "Ravi";
    acc.deposit(1000);
    acc.withdraw(300);

    // acc.balance = -99999;   // <-- uncomment this: it will NOT compile

    cout << acc.owner << "'s balance: " << acc.getBalance() << endl;
    return 0;
}
Expected outputRavi's balance: 700

⚡ Quick guide — try it yourself

  1. Save as bank_account_private.cpp, compile with g++ -std=c++17, run it.
  2. Uncomment the acc.balance = -99999; line and recompile. Read the compiler error carefully — it will say something like 'double BankAccount::balance' is private. That error is the access specifier doing its job.
  3. Try calling acc.withdraw(5000); — confirm it's rejected by the balance check instead of silently going negative.

Every account needs to start in a valid state — and clean up properly when it's closed.

WHY

Why "just remember to initialise it" isn't good enough

In the last tab, if you create a BankAccount and call getBalance() before ever calling deposit(), you get whatever garbage value happened to be in memory — because balance was never initialised. Enterprise bugs caused by uninitialised state are notoriously hard to reproduce. A constructor guarantees every object starts valid, automatically, every single time — no relying on the caller to remember.

WHAT

Default, parameterized, and copy constructors — and the destructor

  • Default constructor — takes no arguments, runs automatically when you write BankAccount acc;.
  • Parameterized constructor — takes arguments, lets you construct an already-populated object in one line: BankAccount acc("Ravi", 1000);
  • Copy constructor — runs when a new object is created from an existing one (BankAccount acc2 = acc1;). The compiler gives you one for free (a shallow, member-by-member copy) if you don't write your own — but for anything managing a resource, write your own to be safe.
  • Destructor — named ~ClassName(), takes no arguments, runs automatically when the object goes out of scope (or is deleted). Use it to release resources — close a file, log an audit trail, free memory.
HOW

All three constructors on BankAccount

Adapted from the course repo's c2withconstructor.cpp pattern:

bank_account_constructors.cpp
#include <iostream>
using namespace std;

class BankAccount {
private:
    string owner;
    double balance;

public:
    // Default constructor — every account starts safely at zero
    BankAccount() {
        owner = "Unnamed";
        balance = 0.0;
        cout << "Default constructor: new empty account created." << endl;
    }

    // Parameterized constructor — open an account with real details
    BankAccount(string ownerName, double openingBalance) {
        owner = ownerName;
        balance = openingBalance;
        cout << "Account opened for " << owner << "." << endl;
    }

    // Copy constructor — e.g. issuing a joint/duplicate account record
    BankAccount(const BankAccount &source) {
        owner = source.owner;
        balance = source.balance;
        cout << "Copy constructor: duplicated account for " << owner << "." << endl;
    }

    void display() {
        cout << owner << "'s balance: " << balance << endl;
    }
};

int main() {
    BankAccount a1;                          // default constructor runs
    BankAccount a2("Meena", 5000);           // parameterized constructor runs
    BankAccount a3 = a2;                     // copy constructor runs

    a1.display();
    a2.display();
    a3.display();
    return 0;
}
Expected outputDefault constructor: new empty account created. Account opened for Meena. Copy constructor: duplicated account for Meena. Unnamed's balance: 0 Meena's balance: 5000 Meena's balance: 5000

HOW

The destructor — closing an account cleanly

bank_account_destructor.cpp
#include <iostream>
using namespace std;

class BankAccount {
public:
    string owner;

    BankAccount(string ownerName) {
        owner = ownerName;
        cout << "Account opened for " << owner << endl;
    }

    // Destructor: same name as the class, preceded by ~.
    // Runs automatically — no manual call needed for stack objects.
    ~BankAccount() {
        cout << "Account closed for " << owner << " — audit log written." << endl;
    }
};

int main() {
    BankAccount a1("Ravi");                      // stack object
    BankAccount* a2 = new BankAccount("Anita");   // heap object

    delete a2;   // explicitly triggers ~BankAccount() for the heap object
    return 0;
    // a1 goes out of scope here -> its destructor runs automatically
}
Expected outputAccount opened for Ravi Account opened for Anita Account closed for Anita — audit log written. Account closed for Ravi — audit log written.

⚡ Quick guide — try it yourself

  1. Save both snippets and compile each with g++ -std=c++17.
  2. In the destructor example, remove the delete a2; line and rerun — notice "Account closed for Anita" never prints. That's a leaked object and a missed audit log.
  3. Predict the print order before running: which destructor fires first, a1's or the manually-deleted a2's? Then check your answer against the output.

Some information belongs to the bank as a whole, not to any one account.

WHY

Why we need data that isn't per-object

"How many accounts has this bank opened in total?" isn't a property of any single BankAccount — it's shared across all of them. If you stored a totalAccounts counter as a normal member, every object would have its own separate copy, each stuck at whatever value it started with. A static member solves this: exactly one copy exists, shared by the class itself and every instance of it.

WHAT

Static data members and static functions

  • Static data member — declared with static inside the class, but must be defined (initialised) once, outside the class, e.g. int BankAccount::totalAccounts = 0;
  • Static member function — can be called via the class name directly (BankAccount::showTotal();), without needing any object. It can only touch other static members — it has no access to a particular object's data.
HOW

Counting every account ever opened

Adapted from the repo's staticmemandfunc.cpp (there it counts Employees; here it counts accounts):

bank_account_static.cpp
#include <iostream>
using namespace std;

class BankAccount {
public:
    int accountId;
    string owner;
    static int totalAccounts;   // declaration only — shared by ALL accounts

    BankAccount(string ownerName) {
        owner = ownerName;
        totalAccounts++;            // every new account bumps the shared counter
        accountId = totalAccounts;  // simple way to assign a unique ID
    }

    void display() {
        cout << "Account #" << accountId << " — " << owner << endl;
    }

    static void showTotal() {
        // static function: no 'this', can only touch static members
        cout << "Total accounts opened: " << totalAccounts << endl;
    }
};

// Definition (and initialisation) of the static member — required exactly once
int BankAccount::totalAccounts = 0;

int main() {
    BankAccount::showTotal();     // callable before any object exists

    BankAccount a1("Ravi");
    BankAccount a2("Meena");
    BankAccount a3("Karan");

    a1.display();
    a2.display();
    a3.display();

    BankAccount::showTotal();     // now reflects all three accounts
    return 0;
}
Expected outputTotal accounts opened: 0 Account #1 — Ravi Account #2 — Meena Account #3 — Karan Total accounts opened: 3

⚡ Quick guide — try it yourself

  1. Save as bank_account_static.cpp, compile with g++ -std=c++17, run it.
  2. Add a 4th account and confirm the total updates to 4 without you touching totalAccounts directly anywhere in main().
  3. Try calling a1.showTotal(); instead of BankAccount::showTotal(); — it still compiles (static members are reachable both ways), but the class-name form is the idiomatic one since it makes clear no specific object is involved.

Private means "not to the world" — but sometimes one specific, trusted class still needs in.

WHY

Why private isn't always absolute

Our BankAccount.balance is private — correctly so. But a real bank has a BankManager role that legitimately needs to adjust balances directly (correcting an error, processing an override) without going through the normal deposit/withdraw rules a regular customer-facing API would enforce. Making balance public just to satisfy this one case would defeat the whole point. C++'s answer is friendship — an explicit, named exception the class itself grants.

WHAT

Friend functions vs friend classes

  • Friend function — a standalone (non-member) function explicitly declared inside the class with the friend keyword. It's not a member, but it can read and write the class's private/protected data.
  • Friend class — an entire class declared as a friend. Every member function of the friend class can then access the private/protected members of the class that granted friendship.
  • Friendship is granted, not taken — BankAccount must explicitly say friend class BankManager; inside its own body. BankManager has no say in the matter, and friendship is one-directional and not inherited.
HOW

BankManager auditing BankAccount — straight from the repo

This exact example already exists in the course repository, built around this precise scenario:

08-ClassesandObjects/friendclass.cpp (excerpt)
#include <iostream>
using namespace std;

class BankAccount {
private:
    double balance;
    string name;
    friend class BankManager;   // grants BankManager access to our private data

public:
    BankAccount(string n, double b) {
        name = n;
        balance = b;
        cout << "Account created for " << name << " with balance " << balance << endl;
    }
};

class BankManager {
public:
    void setBalance(BankAccount &account, double amount) {
        account.balance = amount;   // legal ONLY because of the friend declaration
    }

    double getBalance(BankAccount &account) {
        return account.balance;     // same here
    }
};

int main() {
    BankAccount account("John Doe", 500.0);
    BankManager manager;

    manager.setBalance(account, 1000.0);
    double accbal = manager.getBalance(account);

    cout << "Updated Balance: " << accbal << endl;
    return 0;
}
Expected outputAccount created for John Doe with balance 500 Updated Balance: 1000

⚡ Quick guide — try it yourself

  1. Save the excerpt as friendclass_bank.cpp, compile with g++ -std=c++17, run it.

HOW

A friend function, not a whole friend class

When only one function — not an entire class — needs access, declare just that function as a friend:

08-ClassesandObjects/friendFunction.cpp
#include <iostream>
using namespace std;

class Box {
private:
    double width;
public:
    Box(double w) : width(w) {}

    // Declares printWidth as a friend — defining it right here is
    // just a convenience; it is still NOT a member function.
    friend void printWidth(Box box)
    {
        cout << "Width of box: " << box.width << endl;
        // A friend function is like a trusted guest let into the house (class) —
        // it can see the private furniture, but it doesn't live there.
    }
};

int main() {
    Box box(10.0);
    printWidth(box);   // called like any ordinary function — no box.printWidth()
    return 0;
}
Expected outputWidth of box: 10

Try now: build a safe bank account

We have moved from loose data and functions to a class that protects its own state. This complete program uses a private balance, a constructor, member functions, and a static account counter in one small banking use case.

15 minutes
Step 1Create a class with protected state

Begin with a private balance and one public function that can read it.

step1_class.cpp
#include <iostream>

class BankAccount {
private:
    double balance;

public:
    BankAccount(double openingBalance) : balance(openingBalance) {}
    void printBalance() const {
        std::cout << "Balance: " << balance << std::endl;
    }
};

int main() {
    BankAccount account(1000);
    account.printBalance();
    return 0;
}

Run: g++ -std=c++17 step1_class.cpp -o step1, then step1.exe or ./step1

See: Balance: 1000

Step 2Add safe operations

Put the rules for deposits and withdrawals inside the class instead of changing the balance from main.

step2_operations.cpp
#include <iostream>

class BankAccount {
private:
    double balance;

public:
    BankAccount(double openingBalance) : balance(openingBalance) {}
    void deposit(double amount) { if (amount > 0) balance += amount; }
    bool withdraw(double amount) {
        if (amount <= 0 || amount > balance) return false;
        balance -= amount;
        return true;
    }
    void printBalance() const {
        std::cout << "Balance: " << balance << std::endl;
    }
};

int main() {
    BankAccount account(1000);
    account.deposit(250);
    std::cout << "Withdrawal accepted: "
              << std::boolalpha << account.withdraw(100) << std::endl;
    account.printBalance();
    return 0;
}

Run: g++ -std=c++17 step2_operations.cpp -o step2, then step2.exe or ./step2

See: Withdrawal accepted: true and Balance: 1150

Step 3Share a class-level count

Add a static member so every account contributes to one bank-wide total.

step3_static.cpp
#include <iostream>

class BankAccount {
private:
    static int openAccounts;
public:
    BankAccount() { ++openAccounts; }
    static int accountCount() { return openAccounts; }
};

int BankAccount::openAccounts = 0;

int main() {
    BankAccount first;
    BankAccount second;
    std::cout << "Open accounts: "
              << BankAccount::accountCount() << std::endl;
    return 0;
}

Run: g++ -std=c++17 step3_static.cpp -o step3, then step3.exe or ./step3

See: Open accounts: 2

Now combine the pieces into the complete use case
01
Understand the design before you type

BankAccount owns the balance. The constructor creates a valid starting state. deposit and withdraw control changes. openAccounts is shared by every object. The user of the class cannot write directly to balance.

program.cpp · complete use case
#include <iostream>
#include <string>

class BankAccount {
private:
    std::string owner;
    double balance;
    static int openAccounts;

public:
    BankAccount(const std::string& accountOwner, double openingBalance)
        : owner(accountOwner), balance(openingBalance) {
        ++openAccounts;
    }

    void deposit(double amount) {
        if (amount > 0) balance += amount;
    }

    bool withdraw(double amount) {
        if (amount <= 0 || amount > balance) return false;
        balance -= amount;
        return true;
    }

    void printSummary() const {
        std::cout << owner << " has balance: " << balance << std::endl;
    }

    static int accountCount() { return openAccounts; }
};

int BankAccount::openAccounts = 0;

int main() {
    BankAccount ravi("Ravi", 1000);
    BankAccount maya("Maya", 500);

    ravi.deposit(250);
    maya.withdraw(100);
    ravi.printSummary();
    maya.printSummary();
    std::cout << "Open accounts: " << BankAccount::accountCount() << std::endl;
    return 0;
}
Expected outputRavi has balance: 1250 Maya has balance: 400 Open accounts: 2

Systems Programming & Advanced C++ Internals

Sockets, move semantics, inter-process communication, linking, system diagnostics, and runtime type identification — the systems-level skills underneath every enterprise C++ application that isn't just business logic.

Every distributed system — a chat app, a monitoring agent, a microservice — starts with the same primitive: two processes exchanging bytes over a socket. TCP and UDP are the two transport choices, and picking the wrong one costs you either reliability or latency.

WHY

Two transport protocols, not one

TCP (Transmission Control Protocol) is like registered mail with tracking: it guarantees ordered, reliable, byte-stream delivery — lost packets are retransmitted automatically. That reliability costs a connection setup (the "three-way handshake") and some latency.

UDP (User Datagram Protocol) is like a postcard: fire it and forget it. No ordering guarantee, no retransmission, no connection to set up — but almost zero overhead. It's the right choice when an occasional lost packet is acceptable but added delay is not (video frames, telemetry pings, DNS lookups).

Enterprise systems pick per use case: a payment API uses TCP because losing a byte of a transaction is unacceptable; a live sensor dashboard might use UDP because the next reading is only a second away anyway.

WHAT

The Berkeley sockets vocabulary (Winsock on Windows)

  • WSAStartup(MAKEWORD(2,2), &wsaData) — Windows-only: initializes the Winsock library before any socket call. Every Winsock program needs it once, and WSACleanup() at the end.
  • socket(AF_INET, SOCK_STREAM, 0) — creates an endpoint. AF_INET means IPv4; SOCK_STREAM means TCP, SOCK_DGRAM would mean UDP.
  • bind() — (server) attaches the socket to a local address and port so clients know where to find it.
  • listen() / accept() — (server, TCP only) listen marks the socket as willing to accept connections; accept blocks until a client connects and returns a brand-new socket dedicated to that one client.
  • connect() — (client, TCP) attempts the three-way handshake to a server's address and port.
  • send() / recv() — write and read bytes on a connected TCP socket. UDP uses sendto() / recvfrom() instead, since there's no persistent connection to address.
  • closesocket() — releases the socket (Linux/macOS use the plain close() used for any file descriptor — see the Pipes tab for why sockets and files share that concept).
  • Linking: Windows socket programs need -lws2_32 on the compile line — the Winsock functions live in that import library, not in the standard runtime.
HOW

A minimal TCP server and client exchanging one message

net_server_step.cpp
#include <iostream>
#include <winsock2.h>
#include <string>
using namespace std;

int main() {
    WSADATA wsaData;
    WSAStartup(MAKEWORD(2, 2), &wsaData);

    SOCKET serverSocket = socket(AF_INET, SOCK_STREAM, 0);
    sockaddr_in addr{};
    addr.sin_family = AF_INET;
    addr.sin_port = htons(8080);
    addr.sin_addr.s_addr = INADDR_ANY;
    bind(serverSocket, (sockaddr*)&addr, sizeof(addr));
    listen(serverSocket, 1);

    cout << "(Server) waiting for a connection on port 8080...\n";
    sockaddr_in clientAddr;
    int clientSize = sizeof(clientAddr);
    SOCKET clientSocket = accept(serverSocket, (sockaddr*)&clientAddr, &clientSize);
    cout << "(Server) client connected.\n";

    char buffer[1024] = {0};
    int bytes = recv(clientSocket, buffer, sizeof(buffer) - 1, 0);
    buffer[bytes] = '\0';
    cout << "(Server) received: " << buffer << "\n";

    string reply = "Message received, over.";
    send(clientSocket, reply.c_str(), (int)reply.size(), 0);
    cout << "(Server) sent reply.\n";

    closesocket(clientSocket);
    closesocket(serverSocket);
    WSACleanup();
}
net_client_step.cpp
#include <iostream>
#include <winsock2.h>
#include <string>
using namespace std;

int main() {
    WSADATA wsaData;
    WSAStartup(MAKEWORD(2, 2), &wsaData);

    SOCKET clientSocket = socket(AF_INET, SOCK_STREAM, 0);
    sockaddr_in serverAddr{};
    serverAddr.sin_family = AF_INET;
    serverAddr.sin_port = htons(8080);
    serverAddr.sin_addr.s_addr = inet_addr("127.0.0.1");

    connect(clientSocket, (sockaddr*)&serverAddr, sizeof(serverAddr));
    cout << "(Client) connected to server.\n";

    string message = "Rack-A temperature nominal.";
    send(clientSocket, message.c_str(), (int)message.size(), 0);
    cout << "(Client) sent: " << message << "\n";

    char buffer[1024] = {0};
    int bytes = recv(clientSocket, buffer, sizeof(buffer) - 1, 0);
    buffer[bytes] = '\0';
    cout << "(Client) server replied: " << buffer << "\n";

    closesocket(clientSocket);
    WSACleanup();
}

Copying a vector of ten million elements takes real time and real memory. Move semantics let the compiler transfer ownership of a temporary's internal buffer instead of copying it — turning an expensive deep copy into a handful of pointer swaps.

WHY

lvalues, rvalues, and the cost of "just in case" copies

An lvalue is an expression with a name and a persistent address — a variable you could take the address of. An rvalue is a temporary — the result of a + b, a function's return value, a literal — about to be destroyed the moment the current statement finishes.

Before C++11, a function returning a large object by value always risked a full deep copy: build the object locally, then copy every byte of it into the caller's variable. But if the source is a temporary that's about to disappear anyway, why copy it at all? Nobody will ever read that temporary again — its resources can simply be handed over.

Move semantics formalizes that idea: a move constructor steals the internal pointers/buffers from a soon-to-be-destroyed object instead of duplicating them, leaving the source in a valid-but-empty state.

WHAT

Rvalue references and std::move

  • T& — an lvalue reference; binds only to named, addressable objects.
  • T&& — an rvalue reference; binds only to temporaries (rvalues). A function overloaded on both lets the compiler pick the cheap move path automatically for temporaries.
  • std::move(x) — does not move anything by itself. It's a cast that says "treat x as an rvalue" — permission for the next constructor or assignment to steal from it. #include <utility>.
  • Move constructor / move assignment operator — special members that take a T&& and transfer ownership (pointer copy + null out the source) instead of deep-copying. The compiler generates them automatically for a class whose members are all movable, as long as you haven't declared your own copy constructor/destructor/copy-assignment.
  • Moved-from state — after std::move(x) is used to construct or assign into something else, x is left "valid but unspecified": safe to destroy or reassign, but you must not assume its old contents are still there (a moved-from std::vector is typically empty, but that's not a language guarantee for every type).
HOW

Overload resolution on lvalue vs rvalue, and an explicit std::move

move_step.cpp
#include <iostream>
#include <vector>
using namespace std;

void processVector(vector<int>& vec) {
    cout << "lvalue overload, size=" << vec.size() << "\n";
}
void processVector(vector<int>&& vec) {
    cout << "rvalue overload, size=" << vec.size() << "\n";
}

vector<int> createLarge() {
    vector<int> temp(1000000, 7);
    return temp; // moved (or elided) on return, never copied
}

int main() {
    vector<int> a = {1, 2, 3, 4, 5};
    processVector(a);                    // a is named -> lvalue overload
    processVector(vector<int>{6, 7, 8}); // temporary -> rvalue overload

    cout << "before move, a.size()=" << a.size() << "\n";
    vector<int> b = std::move(a);        // steal a's buffer instead of copying it
    cout << "after move,  a.size()=" << a.size() << " (moved-from)\n";
    cout << "after move,  b.size()=" << b.size() << "\n";

    vector<int> big = createLarge();
    cout << "big.size()=" << big.size() << "\n";
}
Expected outputlvalue overload, size=5 rvalue overload, size=3 before move, a.size()=5 after move, a.size()=0 (moved-from) after move, b.size()=5 big.size()=1000000

Two processes on the same machine that need to hand data to each other don't always need a network socket — a pipe is a simpler, faster channel for exactly that. And every open file, socket, or console in a program is identified by the same underlying idea: a handle into the operating system's table of open resources.

WHY

When you need a second process, not just a second thread

std::thread (Module 7) runs work inside the same process, sharing memory directly. Sometimes that's the wrong isolation level: a flaky third-party parser, a plugin you don't fully trust, or a task that needs its own address space so a crash there doesn't take down your whole service. For that, you spawn a separate process — and processes don't share memory, so they need an explicit channel to exchange data. A pipe is the simplest such channel: a unidirectional byte stream with a write end and a read end.

Every open resource — a file, a socket, a pipe, the console — is tracked by the operating system as a file descriptor on POSIX systems (Linux/macOS), or a HANDLE on Windows. That's why closing a socket and closing a pipe both eventually reduce to "release this handle" — they're the same underlying OS concept wearing different C++ wrapper types.

WHAT

Windows anonymous pipes and process creation

  • CreatePipe(&hRead, &hWrite, &sa, 0) — creates one unidirectional pipe, returning a read HANDLE and a write HANDLE.
  • SetHandleInformation(hWrite, HANDLE_FLAG_INHERIT, 0) — the child process should inherit only the read end; this call stops the write end from leaking into the child too.
  • CreateProcess(...) with STARTUPINFO.hStdInput = hRead and dwFlags = STARTF_USESTDHANDLES — launches a new process and redirects its standard input to the pipe's read end, so the child can simply read from std::cin.
  • WriteFile / ReadFile — raw byte I/O on a HANDLE, the Windows equivalent of POSIX write()/read() on a file descriptor.
  • Closing the write handle signals end-of-file to whatever is reading — exactly like closing a file makes further reads return "no more data."
HOW

Parent writes to a pipe, a child process launched from the same exe reads it

ipc_pipe_step.cpp
#include <windows.h>
#include <iostream>
#include <string>
using namespace std;

void Fail(const char* msg) {
    cerr << msg << " (err=" << GetLastError() << ")\n";
    ExitProcess(1);
}

int child_main() {
    string line;
    if (getline(cin, line))
        cout << "[Child] Received message: " << line << "\n";
    else
        cerr << "[Child] No data read from stdin.\n";
    return 0;
}

int main(int argc, char* argv[]) {
    if (argc >= 2 && string(argv[1]) == "child")
        return child_main();

    SECURITY_ATTRIBUTES sa;
    sa.nLength = sizeof(SECURITY_ATTRIBUTES);
    sa.lpSecurityDescriptor = nullptr;
    sa.bInheritHandle = TRUE;
    HANDLE hRead = nullptr, hWrite = nullptr;
    if (!CreatePipe(&hRead, &hWrite, &sa, 0)) Fail("CreatePipe failed");

    // Only the read end should be inherited by the child
    if (!SetHandleInformation(hWrite, HANDLE_FLAG_INHERIT, 0)) Fail("SetHandleInformation failed");

    char exePath[MAX_PATH];
    GetModuleFileNameA(nullptr, exePath, MAX_PATH);
    string cmd = string("\"") + exePath + "\" child";

    STARTUPINFOA si; PROCESS_INFORMATION pi;
    ZeroMemory(&si, sizeof(si)); ZeroMemory(&pi, sizeof(pi));
    si.cb = sizeof(si);
    si.dwFlags |= STARTF_USESTDHANDLES;
    si.hStdInput = hRead;                              // child's stdin = pipe's read end
    si.hStdOutput = GetStdHandle(STD_OUTPUT_HANDLE);
    si.hStdError  = GetStdHandle(STD_ERROR_HANDLE);

    if (!CreateProcessA(nullptr, &cmd[0], nullptr, nullptr, TRUE, 0, nullptr, nullptr, &si, &pi))
        Fail("CreateProcess failed");

    CloseHandle(hRead); // parent doesn't need the read end

    const char* msg = "Hello from parent via pipe!\n";
    DWORD written = 0;
    WriteFile(hWrite, msg, (DWORD)strlen(msg), &written, nullptr);
    cout << "[Parent] Wrote " << written << " bytes to pipe.\n";
    CloseHandle(hWrite); // closing signals EOF to the child

    WaitForSingleObject(pi.hProcess, INFINITE);
    DWORD exitCode = 0;
    GetExitCodeProcess(pi.hProcess, &exitCode);
    cout << "[Parent] Child exited with code: " << exitCode << "\n";

    CloseHandle(pi.hProcess);
    CloseHandle(pi.hThread);
}
Expected output[Child] Received message: Hello from parent via pipe! [Parent] Wrote 28 bytes to pipe. [Parent] Child exited with code: 0

Note: this program launches itself again with a "child" argument, so a single .exe plays both roles — the "[Child]" line may appear before or after "[Parent] Wrote..." depending on process scheduling.

A finished .cpp file becomes an object file, and object files only become a runnable executable after a linker pulls in every function they call from somewhere — your other .cpp files, or a library. Static linking copies that code into your executable; dynamic linking leaves it in a separate file loaded when the program starts.

WHY

The build pipeline, and why the choice matters

Compiling main.cpp alone doesn't produce a program — it produces an object file (.o) full of machine code and a list of names it still needs (like add or divide) that it didn't define itself. The linker's job is to find those names somewhere else and stitch everything into one executable.

Static linking copies the library's object code directly into your executable at link time. The result is one self-contained file — nothing else needs to be present on the target machine — at the cost of a larger executable, and every program that statically links the same library duplicates that code.

Dynamic linking leaves the library's code in a separate .dll (Windows) or .so (Linux) file. Your executable just stores a reference to it; the OS loader resolves and loads the actual code when the program starts. Multiple programs can share one copy of the library in memory, and the library can be updated (a security patch, say) without recompiling every program that uses it — but the .dll/.so must be present and compatible at runtime, or the program refuses to start.

WHAT

Header, object file, static archive, and shared library

  • Header file (.h) — declares function signatures so the compiler can check calls without seeing the implementation yet.
  • Translation unit → object file (.o) — the compiled-but-not-yet-linked result of one .cpp file.
  • Static library (.a on GCC/MinGW, .lib on MSVC) — an archive of .o files, built with the ar tool. The linker copies only the object files it actually needs from the archive into your executable.
  • Shared/dynamic library (.dll on Windows, .so on Linux) — built with the compiler's -shared flag; contains code that is loaded at runtime rather than copied at link time.
  • -L. tells the linker to also search the current directory for libraries; -lname links against libname.a/libname.so (the lib prefix and extension are added automatically).
HOW

Production services often need to know their own execution environment — how many cores are available, how much memory is free — to size thread pools, caches, or self-reported diagnostics. Unlike file or console I/O, there is no single portable standard-library API for this; you talk to the operating system directly.

WHY

Why this isn't in <iostream>

How many CPU cores exist, how much RAM is installed, what the page size is — these are properties of the operating system and hardware, not of the C++ language. Each OS exposes them through its own API: Windows through the Win32 API (<windows.h>), Linux through virtual files under /proc (/proc/cpuinfo, /proc/meminfo) that look like regular files but are generated on the fly by the kernel.

Enterprise codebases almost always wrap whichever platform API is in play behind their own small SystemInfo abstraction, so the rest of the codebase calls one portable-looking function instead of scattering #ifdef _WIN32 guards everywhere.

WHAT

Win32 system and memory queries, and the one portable exception

  • SYSTEM_INFO + GetSystemInfo(&sysInfo) — fills a struct with dwNumberOfProcessors, dwPageSize, processor architecture, and the addressable memory range.
  • MEMORYSTATUSEX + GlobalMemoryStatusEx(&memStatus) — fills ullTotalPhys / ullAvailPhys (physical RAM) and the virtual-memory equivalents, in bytes.
  • std::thread::hardware_concurrency() — the one genuinely portable equivalent in the standard library. It returns a hint at the number of concurrent threads the hardware can usefully run (0 if it can't determine one) — useful for sizing a thread pool without any platform-specific code.
HOW

Query processor and memory info, then compare with the portable hint

sysinfo_step.cpp
#include <iostream>
#include <windows.h>
#include <sysinfoapi.h>
#include <thread>
using namespace std;

int main() {
    SYSTEM_INFO sysInfo;
    GetSystemInfo(&sysInfo);
    cout << "Number of processors: " << sysInfo.dwNumberOfProcessors << "\n";
    cout << "Page size: " << sysInfo.dwPageSize << " bytes\n";

    MEMORYSTATUSEX memStatus;
    memStatus.dwLength = sizeof(memStatus);
    GlobalMemoryStatusEx(&memStatus);
    cout << "Total physical memory: " << memStatus.ullTotalPhys / (1024 * 1024) << " MB\n";
    cout << "Available physical memory: " << memStatus.ullAvailPhys / (1024 * 1024) << " MB\n";

    // The one genuinely portable equivalent from the standard library:
    cout << "std::thread::hardware_concurrency() = " << thread::hardware_concurrency() << "\n";
}
Expected output (your numbers will differ by machine)Number of processors: 12 Page size: 4096 bytes Total physical memory: 16052 MB Available physical memory: 3086 MB std::thread::hardware_concurrency() = 12

Most polymorphism never needs to ask "what type is this, really?" — a virtual function already routes the call to the right override. But at certain boundaries — a heterogeneous queue of events, a plugin you didn't write, a legacy interface — you need to identify an object's concrete type while the program is running. That's Run-Time Type Information (RTTI).

WHY

The unsafe alternative, and what RTTI protects against

A C-style cast from a base pointer to a derived pointer — (Circle*)shapePtr — compiles and runs even if shapePtr doesn't actually point at a Circle. Nothing checks. The program silently reads memory as if it were a Circle's layout, producing garbage values or a crash somewhere unrelated and hard to trace back.

dynamic_cast is the safe alternative: it consults the same v-table-linked type data the compiler already generates for virtual dispatch, checks whether the conversion is actually valid, and only then hands back a usable pointer or reference. typeid reads that same type data to answer "what is this object's real, most-derived type?" — both require #include <typeinfo> and both only give a run-time answer for polymorphic types (a hierarchy with at least one virtual function, usually the destructor).

WHAT

typeid, dynamic_cast, and when to actually reach for them

  • typeid(expr) — returns a const std::type_info& describing expr's type. On a non-polymorphic type it's a compile-time answer (the declared type); on a polymorphic type (via *pointer or a reference) it's a genuine run-time lookup of the object's actual type.
  • typeid(a) == typeid(b) — compares two types for equality; .name() gives an implementation-defined, often compiler-mangled string — useful for logging, not for user-facing text.
  • dynamic_cast<Derived*>(basePtr) — returns a valid Derived* if the object really is (or derives from) Derived, otherwise nullptr. Check the result before dereferencing.
  • dynamic_cast<Derived&>(baseRef) — the reference form; since a reference can't be null, an impossible cast throws std::bad_cast instead.
  • Polymorphic type identification — using dynamic_cast or typeid at one call site to branch on an object's concrete type, when adding a virtual method to the base class for that one caller's need would leak an unrelated concern into every subtype.
  • Rule of thumb: reach for a virtual function first — it scales better as new subtypes are added. Reach for RTTI only at boundaries you don't fully control, and only for a handful of known types, not as a general substitute for polymorphism.
  • RTTI has a small runtime/binary-size cost and can be disabled with -fno-rtti in performance- or size-sensitive builds (embedded, some game engines) — typeid/dynamic_cast then become compile errors, so this is a deliberate, project-wide decision, not a casual flag.
HOW

Safe downcasting with dynamic_cast, pointer and reference forms

rtti_step.cpp
#include <iostream>
#include <typeinfo>
using namespace std;

struct Shape {
    virtual ~Shape() {}
    virtual double area() const = 0;
};
struct Circle : Shape {
    double radius;
    Circle(double r) : radius(r) {}
    double area() const override { return 3.14159 * radius * radius; }
    void spin() const { cout << "Circle spins in place\n"; }
};
struct Rectangle : Shape {
    double w, h;
    Rectangle(double w_, double h_) : w(w_), h(h_) {}
    double area() const override { return w * h; }
    void stretch() const { cout << "Rectangle stretches its width\n"; }
};

int main() {
    Shape* shapes[] = { new Circle(4.0), new Rectangle(3.0, 5.0) };

    for (Shape* s : shapes) {
        cout << "area = " << s->area() << " -> ";
        if (Circle* c = dynamic_cast<Circle*>(s)) {
            c->spin();
        } else if (Rectangle* r = dynamic_cast<Rectangle*>(s)) {
            r->stretch();
        }
    }

    Circle onlyCircle(2.0);
    Shape& shapeRef = onlyCircle;
    try {
        Circle& c = dynamic_cast<Circle&>(shapeRef);      // succeeds
        cout << "Reference cast succeeded, radius = " << c.radius << "\n";
        Rectangle& r = dynamic_cast<Rectangle&>(shapeRef); // impossible - throws
        cout << r.w;
    } catch (const bad_cast& e) {
        cout << "Caught std::bad_cast: " << e.what() << "\n";
    }

    for (Shape* s2 : shapes) delete s2;
}
Expected outputarea = 50.2654 -> Circle spins in place area = 15 -> Rectangle stretches its width Reference cast succeeded, radius = 2 Caught std::bad_cast: std::bad_cast

🎬 Story Mode

The on-call page that came from the wrong data center

Nimbus Systems' factory-floor sensor rig from Module 7 grew up. It's no longer one batch job on one machine — it's a fleet of diagnostics agents running across a dozen server racks, each one collecting readings, deciding what's urgent, and phoning home to a central relay. The night everything went sideways, an agent's report reached the relay eleven minutes late, formatted wrong, and missing the one line that mattered. Here's every piece of this module, in the order the team added it to make sure that never happened again.

ACT 1

"Phone home, reliably"

The first version of the relay used UDP because it was simpler to write. It worked fine in testing — then, on a congested night, three agents' reports vanished into the network with no error, no retry, nothing. The team switched the relay link to TCP: slightly more setup cost per connection, but every report is now acknowledged or the agent knows it failed and can retry. UDP stayed in use for a different, lower-stakes channel — a once-a-second "still alive" heartbeat where losing an occasional ping is fine.

ACT 2

"Eleven minutes started here"

Each agent builds its readings into a buffer, then hands it to the formatter, then to the network layer — three function boundaries. The original code copied that buffer at every handoff. On a quiet rack that was invisible; on the rack with 40,000 readings queued up during an incident, three unnecessary deep copies of a multi-megabyte buffer were exactly where those eleven minutes went. Returning the buffer by value and letting the compiler move it, plus one explicit std::move at the formatter handoff, took that cost to nearly zero.

ACT 3

"Isolating the log-rotation helper"

Each agent's disk-log rotation was handled by a small helper that occasionally hung on a locked file. Running it as a thread meant a hang there could stall the whole agent. The fix: spawn it as a separate child process and hand it its work over a pipe. If the helper hangs now, the parent agent notices the pipe never gets an EOF, kills the child, and keeps reporting — the crash (or hang) is contained to a process boundary instead of taking down the reporting loop with it.

ACT 4

"The rack still running last month's binary"

The agent statically linked its math and formatting helpers, so a bug fix in the formatting library meant rebuilding and redeploying every single agent binary across every rack — including the rack that turned out to still be running a build from three releases ago, because nobody had a clean way to tell. Splitting the shared formatting code into a dynamically linked library meant one file could be pushed to every rack and picked up on next restart, without touching the agent binary itself — and a version-stamped .dll made "which build is this rack running?" a one-line check instead of a mystery.

ACT 5

"Was it actually out of memory, or just slow?"

The incident report that started this whole rewrite blamed "memory pressure" on the slow rack — but nobody had actually checked. The team added a one-line system snapshot (processor count, available physical memory, hardware_concurrency()) to every report the agent sends. The next time a rack looked slow, the diagnostic answer took five seconds to read instead of a guess: it wasn't memory at all, it was the network switch on that one rack running half-duplex.

ACT 6

"Not every alert deserves the same threshold"

The diagnostics queue mixes temperature, disk, and network events in one vector<unique_ptr<DiagnosticEvent>>, because they all need the same describe() and the same transport. But "is this one critical?" depends on completely different thresholds per event kind — and adding a virtual isCritical() to the base class would force every future event type to invent a threshold rule whether it has one or not. A short dynamic_cast chain at the one place that actually needs it — the alert gate right before sending — kept each event class focused on its own data.

Sockets get the bytes there. Move semantics make sure getting them there doesn't cost more than it has to. Pipes contain the parts you don't trust. Linking decides how fast a fix reaches every machine. System info turns "it feels slow" into a number. And RTTI, used sparingly, lets one honest exception to "just use a virtual function" through the door without breaking the rule for everyone else.

Also seen in the wild

FinanceTrading gateways dynamically link their FIX protocol library so a protocol patch ships without recompiling every trading strategy binary.
Game enginesAsset pipelines spawn a separate texture-compression process over a pipe, so a malformed asset crashes the compressor, not the editor.
BrowsersA renderer process reports its own memory footprint to the browser's process manager, which decides whether to throttle or kill a runaway tab.
Plugin systemsA host application receiving third-party Plugin* objects uses dynamic_cast to check for optional capability interfaces (e.g. IConfigurable) a given plugin may or may not implement.
Bring it back: the complete program below is the Nimbus fleet diagnostics agent — it builds its readings and moves them ownership-first, identifies each event's real type to decide what's critical, and sends the finished report to a relay server over TCP. Pipes, linking, and system info stay as their own dedicated systems-level exercises in this module, because in real deployments they live at the process and build-pipeline level, not inside one client's send loop.

Step 2Identify each event's real type to decide "is this critical?"

dynamic_cast checks the object's real, run-time type before applying that type's own threshold rule.

step2_identify.cpp
#include <iostream>
#include <memory>
#include <vector>
#include <string>
using namespace std;

struct DiagnosticEvent {
    string source;
    DiagnosticEvent(string s) : source(move(s)) {}
    virtual ~DiagnosticEvent() {}
    virtual string describe() const { return source + ": generic event"; }
};
struct TempEvent : DiagnosticEvent {
    double celsius;
    TempEvent(string s, double c) : DiagnosticEvent(move(s)), celsius(c) {}
    string describe() const override { return source + ": temperature " + to_string(celsius) + "C"; }
};
struct DiskEvent : DiagnosticEvent {
    int percentFull;
    DiskEvent(string s, int pct) : DiagnosticEvent(move(s)), percentFull(pct) {}
    string describe() const override { return source + ": disk " + to_string(percentFull) + "% full"; }
};

bool isCritical(const DiagnosticEvent& e) {
    if (auto* t = dynamic_cast<const TempEvent*>(&e)) return t->celsius > 90.0;
    if (auto* d = dynamic_cast<const DiskEvent*>(&e)) return d->percentFull > 90;
    return false;
}

int main() {
    vector<unique_ptr<DiagnosticEvent>> events;
    events.push_back(make_unique<TempEvent>("Rack-A", 94.5));
    events.push_back(make_unique<DiskEvent>("Rack-B", 42));
    for (const auto& e : events) {
        cout << e->describe();
        if (isCritical(*e)) cout << " [CRITICAL]";
        cout << "\n";
    }
}

Step 3Send the finished report to a relay over TCP

Two files, two terminals — same connect/send pattern from the Networking tab, now carrying a real multi-line report.

step3_relay_server.cpp
#include <iostream>
#include <winsock2.h>
using namespace std;

int main() {
    WSADATA wsaData;
    WSAStartup(MAKEWORD(2, 2), &wsaData);
    SOCKET serverSocket = socket(AF_INET, SOCK_STREAM, 0);
    sockaddr_in addr{};
    addr.sin_family = AF_INET;
    addr.sin_port = htons(9090);
    addr.sin_addr.s_addr = INADDR_ANY;
    bind(serverSocket, (sockaddr*)&addr, sizeof(addr));
    listen(serverSocket, 1);
    cout << "[Relay] Listening on port 9090...\n";
    sockaddr_in clientAddr; int clientSize = sizeof(clientAddr);
    SOCKET clientSocket = accept(serverSocket, (sockaddr*)&clientAddr, &clientSize);
    cout << "[Relay] Agent connected.\n";
    char buffer[4096] = {0};
    int bytes = recv(clientSocket, buffer, sizeof(buffer) - 1, 0);
    if (bytes > 0) { buffer[bytes] = '\0'; cout << "[Relay] Report received:\n" << buffer << "\n"; }
    closesocket(clientSocket);
    closesocket(serverSocket);
    WSACleanup();
}

Fleet diagnostics agent — move semantics, RTTI, and networking together

Collects readings with a moved buffer, classifies each with dynamic_cast, formats one report, and sends it to the relay server from Step 3.

program.cpp — complete use case
#include <iostream>
#include <winsock2.h>
#include <memory>
#include <vector>
#include <string>
#include <sstream>
using namespace std;

struct DiagnosticEvent {
    string source;
    DiagnosticEvent(string s) : source(move(s)) {}
    virtual ~DiagnosticEvent() {}
    virtual string describe() const { return source + ": generic event"; }
};
struct TempEvent : DiagnosticEvent {
    double celsius;
    TempEvent(string s, double c) : DiagnosticEvent(move(s)), celsius(c) {}
    string describe() const override { return source + ": temperature " + to_string(celsius) + "C"; }
};
struct DiskEvent : DiagnosticEvent {
    int percentFull;
    DiskEvent(string s, int pct) : DiagnosticEvent(move(s)), percentFull(pct) {}
    string describe() const override { return source + ": disk " + to_string(percentFull) + "% full"; }
};

bool isCritical(const DiagnosticEvent& e) {
    if (auto* t = dynamic_cast<const TempEvent*>(&e)) return t->celsius > 90.0;
    if (auto* d = dynamic_cast<const DiskEvent*>(&e)) return d->percentFull > 90;
    return false;
}

// builds the day's readings into one buffer, then hands ownership to the
// caller via a move - the vector of unique_ptr could not be copied anyway
vector<unique_ptr<DiagnosticEvent>> collectReadings() {
    vector<unique_ptr<DiagnosticEvent>> readings;
    readings.push_back(make_unique<TempEvent>("Rack-A", 94.5));
    readings.push_back(make_unique<DiskEvent>("Rack-B", 42));
    readings.push_back(make_unique<DiskEvent>("Rack-D", 97));
    return readings;
}

int main() {
    vector<unique_ptr<DiagnosticEvent>> readings = collectReadings();

    ostringstream report;
    report << "=== Fleet Diagnostics Report ===\n";
    for (const auto& e : readings) {
        report << e->describe();
        if (isCritical(*e)) report << " [CRITICAL]";
        report << "\n";
    }
    string finalReport = report.str();
    cout << finalReport;

    WSADATA wsaData;
    WSAStartup(MAKEWORD(2, 2), &wsaData);
    SOCKET sock = socket(AF_INET, SOCK_STREAM, 0);
    sockaddr_in serverAddr{};
    serverAddr.sin_family = AF_INET;
    serverAddr.sin_port = htons(9090);
    serverAddr.sin_addr.s_addr = inet_addr("127.0.0.1");

    if (connect(sock, (sockaddr*)&serverAddr, sizeof(serverAddr)) == 0) {
        send(sock, finalReport.c_str(), (int)finalReport.size(), 0);
        cout << "Report sent to relay.\n";
    } else {
        cout << "Could not reach relay (start relay_server.exe first).\n";
    }
    closesocket(sock);
    WSACleanup();
}

Note: start relay_server.exe from Step 3 first, in its own terminal — the agent's "Could not reach relay" message is the expected, non-crashing result of running the agent alone.

Advanced C++ Features

Lambdas, smart pointers, file I/O, and multithreading — the four pillars that separate a working program from a production-grade one.

Day: 4 of 6Topics: 4 + Story ModeCase study: Concurrent sensor log aggregatorRepo folder: 17-Threading/, 15-Smart_Pointers/, 11-FStream/

STL algorithms expect callable predicates and comparators. Before lambdas, every one-line callback required a named function or a functor class. Lambdas let you write the callback where you use it — no naming, no boilerplate, no separate function definition.

WHY

Named functions for one-time callbacks

Suppose you want to sort students by grade. You write bool byGradeDesc(const Student& a, const Student& b), use it once in std::sort, and it pollutes your namespace forever.

Multiply that by every unique sort order, every unique filter predicate, every std::transform operation — and you have dozens of tiny named functions that exist only to be passed to one algorithm call.

A lambda is an anonymous function expression. You write the body exactly where the callback goes — the compiler generates a unique unnamed callable type. It exists in scope only for that one use, and it can capture local variables from the surrounding scope.

WHAT

Lambda syntax and captures

  • [](params) { body } — basic lambda; no captures, explicit params, return type deduced.
  • [=](params) { body } — capture all local variables by value (copy). Safe for threads that outlive the enclosing scope.
  • [&](params) { body } — capture all local variables by reference. Faster (no copy) but dangerous if the lambda outlives the variable.
  • [x, &y](params) { body } — capture x by value, y by reference — minimal and explicit.
  • -> ReturnType — explicit return type after ); required when the compiler can't deduce it (e.g., multiple return paths returning different types).
  • std::function<Ret(Params...)> — type-erased wrapper that can store any callable, including lambdas, at the cost of a small runtime overhead. Use auto when you don't need to store the lambda in a heterogeneous container.
HOW

Filter, sort, and accumulate with lambdas

step1_lambda.cpp
#include <iostream>
#include <vector>
#include <algorithm>
#include <functional>
#include <numeric>
#include <string>

int main() {
    std::vector<int> nums = {3, 1, 4, 1, 5, 9, 2, 6};

    int threshold = 4;
    auto isAbove = [threshold](int n){ return n > threshold; };
    int count = std::count_if(nums.begin(), nums.end(), isAbove);
    std::cout << "Values above " << threshold << ": " << count << "\n";

    // Sort descending — lambda comparator inline
    std::sort(nums.begin(), nums.end(), [](int a, int b){ return a > b; });
    for (int n : nums) std::cout << n << " ";
    std::cout << "\n";

    // Capture by reference to accumulate into outer variable
    int total = 0;
    std::for_each(nums.begin(), nums.end(), [&total](int n){ total += n; });
    std::cout << "Total: " << total << "\n";

    // Store lambda in std::function for later use
    std::function<std::string(const std::string&)> toUpper = [](const std::string& s) {
        std::string r = s;
        std::transform(r.begin(), r.end(), r.begin(), ::toupper);
        return r;
    };
    std::cout << toUpper("hello world") << "\n";
}
Expected outputValues above 4: 3 9 6 5 4 3 2 1 1 Total: 31 HELLO WORLD

Raw new and delete are error-prone: forget one delete and you have a memory leak; call it twice and the program crashes; use the pointer after delete and you have undefined behaviour. Smart pointers automate the lifetime of heap objects so none of those bugs are possible.

WHY

The three ways raw pointers fail

Leak: Sensor* s = new Sensor("A"); return; — if the function returns early (exception or early return), delete s never runs. The sensor object lives forever, its memory is never returned.

Double-delete: Two code paths both call delete s — the second delete corrupts the heap and usually crashes the program in an unrelated location, making the bug hard to find.

Use-after-free: delete s; s->read(); — the pointer is still non-null after delete; accessing it is undefined behaviour. The program might crash, return garbage, or silently corrupt other data.

Smart pointers eliminate all three. The object is owned by the smart pointer, which deletes it in its destructor — exactly once, as soon as the last owner leaves scope.

WHAT

Three smart pointer types

  • std::unique_ptr<T> — sole owner. One object, one unique_ptr. When it goes out of scope, the object is deleted. Move-only: no copy constructor. Create with std::make_unique<T>(constructor_args...).
  • std::shared_ptr<T> — shared ownership. Multiple shared_ptrs can point to the same object. An internal reference count tracks owners; when the last one is destroyed (count reaches 0), the object is deleted. Create with std::make_shared<T>(args...).
  • std::weak_ptr<T> — non-owning observer. Points to a shared_ptr-managed object without incrementing the ref count. Call .lock() to get a temporary shared_ptr — returns nullptr if the object was already deleted. Used to break ownership cycles.
  • Rule of thumb: default to unique_ptr. Upgrade to shared_ptr only when ownership genuinely needs to be shared. Use weak_ptr only to break cycles.
HOW

unique_ptr factory, shared_ptr ref counting, vector of unique_ptrs

step2_smart_ptrs.cpp
#include <iostream>
#include <memory>
#include <vector>
#include <string>

class Sensor {
    std::string id_;
    int reading_;
public:
    Sensor(const std::string& id, int r) : id_(id), reading_(r) {
        std::cout << "Sensor " << id_ << " created\n";
    }
    ~Sensor() { std::cout << "Sensor " << id_ << " destroyed\n"; }
    int read() const { return reading_; }
    const std::string& id() const { return id_; }
};

std::unique_ptr<Sensor> makeSensor(const std::string& id, int val) {
    return std::make_unique<Sensor>(id, val);
}

int main() {
    // unique_ptr: sole owner, auto-deleted on scope exit
    {
        auto s = makeSensor("TMP-01", 72);
        std::cout << "Reading: " << s->read() << "\n";
    } // s destroyed here

    // shared_ptr: reference counting
    std::shared_ptr<Sensor> shared = std::make_shared<Sensor>("HUM-01", 65);
    {
        std::shared_ptr<Sensor> copy = shared; // count = 2
        std::cout << "Count: " << shared.use_count() << "\n";
    } // copy destroyed, count = 1
    std::cout << "Count after inner scope: " << shared.use_count() << "\n";

    // vector of unique_ptrs — move semantics, no raw delete
    std::vector<std::unique_ptr<Sensor>> fleet;
    fleet.push_back(std::make_unique<Sensor>("CO2-01", 420));
    fleet.push_back(std::make_unique<Sensor>("CO2-02", 450));
    for (const auto& s : fleet)
        std::cout << s->id() << ": " << s->read() << "\n";
} // fleet destroyed — all sensors deleted automatically
Expected outputSensor TMP-01 created Reading: 72 Sensor TMP-01 destroyed Sensor HUM-01 created Count: 2 Count after inner scope: 1 Sensor CO2-01 created Sensor CO2-02 created CO2-01: 420 CO2-02: 450 Sensor CO2-02 destroyed Sensor CO2-01 destroyed Sensor HUM-01 destroyed

A program that cannot read and write files cannot store anything permanently. std::fstream gives you the same << and >> operators you already know from std::cout and std::cin, applied to files — with RAII guaranteeing the file is always closed.

WHY

Files, portability, and RAII

The C standard library's fopen/fclose returns raw FILE* — if you forget to call fclose, the file stays locked and data may be lost. On Windows, a locked file prevents other programs from reading it.

std::ofstream and std::ifstream are objects. The file is opened in the constructor and closed in the destructor — RAII guarantees the file is always closed even when an exception propagates. No explicit close() call needed (though calling it early to flush and release is fine).

The << and >> insertion/extraction operators work the same way as with std::cout/std::cin, so there is almost no new syntax to learn.

WHAT

File stream types and key operations

  • std::ofstream out("file.txt") — opens for writing; creates the file if it doesn't exist, truncates if it does.
  • std::ifstream in("file.txt") — opens for reading; in.is_open() returns false if the file doesn't exist.
  • std::fstream fs("file.txt", std::ios::in | std::ios::out) — read+write; use mode flags to control behaviour.
  • Mode flags: std::ios::app (append, don't truncate), std::ios::binary (binary mode, no newline translation).
  • std::getline(in, line) — reads an entire line including spaces, stopping at \n. Returns the stream, so works in a while condition.
  • out.flush() — forces buffered data to disk without closing; useful between write and read on the same file.
HOW

Write a report to disk, read it back line by line

step3_fileio.cpp
#include <iostream>
#include <fstream>
#include <string>
#include <stdexcept>

void writeReport(const std::string& path) {
    std::ofstream out(path);
    if (!out.is_open())
        throw std::runtime_error("Cannot write to: " + path);
    out << "Student Report\n";
    out << "==============\n";
    out << "Alice,92\n";
    out << "Bob,78\n";
    out << "Carol,85\n";
} // out destroyed, file closed automatically

void readReport(const std::string& path) {
    std::ifstream in(path);
    if (!in.is_open())
        throw std::runtime_error("Cannot read: " + path);
    std::string line;
    while (std::getline(in, line))
        std::cout << "[READ] " << line << "\n";
}

int main() {
    const std::string path = "report.txt";
    try {
        writeReport(path);
        std::cout << "Written to " << path << "\n";
        readReport(path);
    }
    catch (const std::runtime_error& e) {
        std::cout << "File error: " << e.what() << "\n";
    }
}
Expected outputWritten to report.txt [READ] Student Report [READ] ============== [READ] Alice,92 [READ] Bob,78 [READ] Carol,85

A modern CPU has 8 to 24 cores. A single-threaded program uses one. std::thread lets you run independent tasks simultaneously — but sharing data between threads safely requires explicit synchronization.

WHY

Parallel work without data races

A data race is when two threads read and write the same variable without coordination. The result is undefined behaviour — the program might produce wrong output, crash, or appear to work correctly only in tests.

std::mutex (mutual exclusion) prevents a data race by ensuring only one thread executes a protected section at a time. std::lock_guard acquires the mutex on construction and releases it when it goes out of scope — RAII applied to locks.

std::async launches a task on a background thread and returns a std::future<T>. Calling .get() on the future blocks until the result is ready. This "fire and collect later" pattern avoids manual thread management for independent computations.

WHAT

Thread, mutex, and async

  • std::thread t(callable, args...) — launches callable(args...) on a new OS thread. Must call t.join() (wait for completion) or t.detach() (let it run independently) before t is destroyed.
  • std::mutex m — non-copyable lock. m.lock() / m.unlock() — use std::lock_guard<std::mutex> lg(m) instead so the unlock is guaranteed even on exception.
  • std::lock_guard<std::mutex> lg(m) — acquires m on construction, releases in destructor. Cannot be used across scopes; use std::unique_lock for that.
  • std::async(std::launch::async, fn, args...) — runs fn(args...) asynchronously. Returns std::future<ReturnType>. Call future.get() to retrieve the result (blocks if not yet ready).
  • std::ref(var) — wraps a variable in a reference wrapper so it can be passed to a thread or async function without copying.
HOW

Two threads summing batches, then async for a one-liner

step4_threads.cpp
#include <iostream>
#include <thread>
#include <mutex>
#include <future>
#include <vector>
#include <numeric>

std::mutex print_mutex;

void processBatch(int id, const std::vector<int>& data, int& result) {
    result = std::accumulate(data.begin(), data.end(), 0);
    std::lock_guard<std::mutex> lock(print_mutex);
    std::cout << "Thread " << id << " sum: " << result << "\n";
}

int main() {
    std::vector<int> b1 = {1, 2, 3, 4, 5};
    std::vector<int> b2 = {6, 7, 8, 9, 10};
    int r1 = 0, r2 = 0;

    std::thread t1(processBatch, 1, std::cref(b1), std::ref(r1));
    std::thread t2(processBatch, 2, std::cref(b2), std::ref(r2));
    t1.join();
    t2.join();

    std::cout << "Combined: " << r1 + r2 << "\n";

    // async: fire a task, collect result later
    auto fut = std::async(std::launch::async, []{
        int s = 0;
        for (int i = 1; i <= 100; ++i) s += i;
        return s;
    });
    std::cout << "Async sum 1-100: " << fut.get() << "\n";
}
Expected output (thread print order may vary)Thread 1 sum: 15 Thread 2 sum: 40 Combined: 55 Async sum 1-100: 5050

Note: The two "Thread" lines may appear in either order depending on scheduling; "Combined" and "Async" always appear last.

Run it and experiment

  1. Compile: g++ -std=c++17 step4_threads.cpp -o step4, run (standard thread links fine on all platforms).
  2. Experiment 1: Remove lock_guard around the print statement and run many times — occasionally the two cout lines will interleave (corrupted output), demonstrating the race.

🎬 Story Mode

The pipeline that kept crashing at midnight

Nimbus Systems monitors a factory floor with 48 sensors — temperature, humidity, CO2, and pressure. Every night at midnight, a batch job collects the day's readings, computes statistics, writes a report to disk, and pages an operator if any sensor drifted outside safe limits. For six months, the job ran single-threaded. With 48 sensors and hundreds of readings each, it took 11 minutes and occasionally missed its window. The team rewrote it using the four features in this module — lambdas, smart pointers, file I/O, and threads — and brought the runtime to under 40 seconds.

ACT 1 — "Inline logic, no name tax"

The original code had 23 one-time comparison functions scattered across 4 files. Every time someone added a new sensor type, they added two more functions. After switching to lambdas, the sort-by-average, the outlier filter, and the threshold check all live exactly where they are used — next to the std::sort, the std::copy_if, and the std::count_if that call them. Zero named functions added to the global scope. Every predicate is co-located with its algorithm.

ACT 2 — "Memory that cleans itself up"

The old batch job created one Sensor* per device and stored them in a std::vector<Sensor*>. After the job finished, a cleanup loop called delete on each pointer. It worked — until a refactor added an early return on parse error, and the cleanup loop was never reached. Six sensors leaked every time the file was malformed. Replacing Sensor* with std::unique_ptr<Sensor> and make_unique meant the sensors destroyed themselves whenever their unique_ptr went out of scope, regardless of which path the code took.

ACT 3 — "The audit trail"

Regulatory compliance required that every batch run's output be preserved on disk for 90 days. The team added a writeReport(path) function using std::ofstream — same << syntax as std::cout, file closed automatically by the destructor. A subsequent readReport function with std::ifstream and getline let the next shift's engineer replay any night's output without touching the database. The RAII guarantee meant no file was ever left open even when a sensor threw a parse exception mid-run.

ACT 4 — "Eleven minutes to forty seconds"

The original single-threaded loop processed sensors one at a time. With 48 sensors averaging 4 seconds of I/O and computation each, runtime was 192 seconds. The rewrite launched one std::thread per sensor group, using a std::mutex around the shared log vector and std::lock_guard to guarantee release. Four groups of 12 sensors ran in parallel. Wall-clock time dropped to under 40 seconds on the same hardware — a 5x speedup from four lines of thread code and six lines of mutex protection.

Lambdas let you write the logic where you need it. Smart pointers make memory manage itself. File I/O persists results without fuss. Threads use the other 15 cores. Together they turn a working program into a production-grade one.

Step 2Filter readings with a lambda

Inline predicate captures limit by value — no named function, no namespace pollution.

#include <iostream>
#include <vector>
#include <algorithm>
int main() {
    std::vector<int> temps = {68, 75, 102, 71, 99, 73};
    int limit = 95;
    auto alerts = std::count_if(temps.begin(), temps.end(),
                                [limit](int t){ return t > limit; });

    std::for_each(temps.begin(), temps.end(), [limit](int t){

Now combine the pieces into the complete use case
01
Concurrent sensor log aggregator — threads, smart pointers, lambdas, and file I/O together

Each sensor runs in its own thread; a mutex guards the shared log; a lambda sorts entries before they are written to disk.

program.cpp — complete use case
#include <iostream>
#include <fstream>
#include <thread>
#include <mutex>
#include <memory>
#include <vector>
#include <string>
#include <algorithm>
#include <numeric>
#include <sstream>
#include <iomanip>

std::mutex log_mutex;
std::vector<std::string> log_entries;

class Sensor {
    std::string id_;
    std::vector<int> readings_;
public:
    Sensor(const std::string& id, std::vector<int> vals)
        : id_(id), readings_(std::move(vals)) {}

    void processAndLog() {
        double avg = static_cast<double>(
            std::accumulate(readings_.begin(), readings_.end(), 0))
            / readings_.size();
        auto [minIt, maxIt] = std::minmax_element(readings_.begin(), readings_.end());

        std::ostringstream oss;
        oss << std::fixed << std::setprecision(1)
            << id_
            << " | avg=" << avg
            << " min=" << *minIt
            << " max=" << *maxIt;

        std::lock_guard<std::mutex> lock(log_mutex);
        log_entries.push_back(oss.str());
    }
};

void writeLog(const std::string& path) {
    std::ofstream out(path);
    for (const auto& entry : log_entries)
        out << entry << "\n";
}

int main() {
    std::vector<std::unique_ptr<Sensor>> sensors;
    sensors.push_back(std::make_unique<Sensor>("TMP-01",
        std::vector<int>{72, 74, 71, 75, 73}));
    sensors.push_back(std::make_unique<Sensor>("HUM-01",
        std::vector<int>{65, 67, 63, 68, 66}));
    sensors.push_back(std::make_unique<Sensor>("CO2-01",
        std::vector<int>{420, 435, 410, 445, 430}));

    // Each sensor processed in its own thread
    std::vector<std::thread> threads;
    for (int i = 0; i < static_cast<int>(sensors.size()); ++i)
        threads.emplace_back([i, &sensors]{ sensors[i]->processAndLog(); });

    for (auto& t : threads) t.join();

    // Sort log entries alphabetically (lambda comparator)
    std::sort(log_entries.begin(), log_entries.end(),
              [](const std::string& a, const std::string& b){ return a < b; });

    std::cout << "=== Sensor Report ===\n";
    for (const auto& e : log_entries) std::cout << e << "\n";

    writeLog("sensor_log.txt");
    std::cout << "\nLog written to sensor_log.txt\n";
}
Expected output=== Sensor Report === CO2-01 | avg=428.0 min=410 max=445 HUM-01 | avg=65.8 min=63 max=68 TMP-01 | avg=73.0 min=71 max=75 Log written to sensor_log.txt

Note: thread print order in processAndLog may vary, but std::sort ensures the final displayed order is always alphabetical.
